# R1 验证与限制

## 实际完成的检查

1. **正式来源与保存**：在现有账号的“由我创建”中打开原 Skill，实际 URL 中的原对象 ID 与给定历史标识对应。重新下载保存前包，读取主文、两个引用和元数据后增量编辑；从编辑器逐文件复制读回，四份文字与准备稿一致，再点击原对象“保存更改”。
2. **持久化**：在新页面重新打开同一对象，并通过其官方下载操作重新取得 ZIP。主文、两个引用与准备稿字节一致；图标原样保留；元数据由服务端去除引号、折行，解析后的 YAML 与准备稿相等。审核副本以保存后实际下载的字节为准，不以准备稿冒充正式版本。
3. **云端引用**：在重新打开的详情页分别点击两个 `references/` 文件并读取全文，包含各文件末段。此前关于引用读取失败的历史记录没有被当作本轮结果。
4. **格式与结构**：既有 `quick_validate.py` 返回 `Skill is valid!`；最终仍为原 5 文件，仅 4 文件发生变化。主文为 95 行，详细模板继续位于引用。主文指向的两个引用可解析，原名称、显示名称、图标、`policy.products`、`allow_implicit_invocation` 和原依赖状态保持。
5. **差异可追溯**：`changes.patch` 由前后两份正式下载文件生成。执行 `python3 verify_review.py` 校验最终 5 文件 SHA-256，再在临时目录反向应用补丁；重建的 5 个原文件全部匹配保存前包哈希。
6. **针对性场景**：对更新要求中的 12 个合成输入逐项作规则桌面推演，具体输入、输出和依据见 `scenario-results.json`。12 项均符合附件预期。该步骤由本执行代理完成，没有启动独立子代理、第二模型、自动工作流或真实业务项目；不能据此宣称自动加载、跨端运行或用户验收通过。

格式校验的 Python 环境最初缺少 PyYAML。仅在本任务隔离目录补齐该校验依赖后重跑成功，没有修改 Skill、插件或业务运行环境的依赖。

## 原优化保留核对

| 既有约束 | 本次保留方式 |
| --- | --- |
| 一项任务一个主流程；普通软件问答不触发协作 | 保留聚焦描述与“入口与分工” |
| 规划、实施、用户关键判断分开 | 原角色分工保留 |
| 不重复申请已有批准；不顺带换技术栈或 UI | 保留继承规则，只把动作权限拆分得更明确 |
| 缺一项材料不停止全部工作 | 保留局部暂停，并扩展到失效附件 |
| 模拟、运行、安装、发布、验收分开 | 扩展为可分别记录的状态；未合并任何验收层次 |
| 新文件与未提交工作须纳入审核 | 保留普通 diff 不包含未跟踪文件的提醒 |
| 审核源码版本与审核仓库提交分开 | 保留，补充固定提交读回与旧 HEAD 的限制 |
| 不假定同账号、同名对象或文件链接即互通 | 保留，逐项记录正文、附件、通知、发送与自动启动能力 |
