# 怎样逐步补充 AM 的工作知识

本包支持把业务资料、工作原则、处理案例、沟通偏好保存为有来源、有版本、有适用范围的知识。默认先形成候选，经过 owner 明确批准后，才进入普通知识检索。

这套机制改变的是机器人在处理问题时可读取的资料，不会自动训练或微调模型。它没有连接 ChatGPT 个人账户记忆。日常对话中的每句话也不会自动成为长期规则。

本指南对应本包的本地导入与对话处理接口。原 AM 仍需由接续端完成实际接入；本地导入成功不能单独证明飞书机器人已经读取到这些资料。

## 1. 从真实纠正开始，一次补充一小条

不需要先写完一套公司百科。可以先整理几个经常遇到、又容易处理错的场景。

建议每次保留以下四部分：

1. **当时发生什么。** 对方说了什么，涉及哪个项目，已有资料有哪些。
2. **你希望怎么处理。** 先核实什么，哪些工作可以继续，需要谁作决定。
3. **为什么这样处理。** 判断所依赖的条件，哪些情况不适用。
4. **这条内容适用到哪里。** 本次情况、某个项目，还是较普遍的工作原则。

例如，下面是一条待业务确认的合成纠正：

> 对方只说“测试做完了”时，先区分测试操作完成与验收通过。需要有对应证据，才能把验收状态写成通过。本次缺的是报告，所以先保留待核，不阻塞能够继续的准备工作。

如果这只是一次特殊处理，保存为 `case`。只有你明确希望以后在同样条件下采用，才整理成 `rule`。类似“这次先不提醒”的话，不应扩展成“以后都不提醒”。

表达习惯也可以逐条补充，例如“问进度时先答当前状态，再给最影响下一步的一件事”。这应记录为待确认的 `style`，不能因此改变事实、承诺日期或执行权限。

## 2. 选择知识类型

| `kind` | 适合保存什么 | 使用时需要注意什么 |
| --- | --- | --- |
| `business` | 产品说明、术语、流程与交付物定义 | 保留来源版本，说明适用产品或流程。 |
| `rule` | 已明确采用的工作原则与判断条件 | 写清条件和例外，不把一次处理直接升为长期规定。 |
| `case` | 当时情境、处理方式、依据和结果 | 案例能帮助比较，但不能保证新情况必然适用。 |
| `style` | 你明确确认的工作沟通偏好与示例 | 学习表达方式时，仍需尊重事实与权限。 |
| `fact` | 带来源的具体事实或待核实反馈 | 动态进度应优先结合项目读取端口核对；同事报告不等于已经验收。 |

当前模块中，非 owner 只能提交 `private` 范围的候选 `fact`。他们不能借导入文件创建共享规则、批准知识，或声明自己是 owner。

## 3. 先确定可见范围

| `scope` | 检索范围 | 配置要求 |
| --- | --- | --- |
| `private` | 当前租户、应用、本人、聊天与线程共同确定的私有会话 | 默认值；可关联一个有权限的 `project_id`。换聊天或换线程不会隐式带出。 |
| `project` | 当前有权限访问的指定项目 | 必须提供 `project_id`，并通过当前项目权限校验。 |
| `tenant` | 当前租户与当前应用的工作知识范围 | 不携带 `project_id`；并非跨应用或跨租户公开。 |

**owner 的治理权限不会扩大资料可见范围。** owner 不能自动查看或批准其他同事私有会话中的候选。工程师在私聊里报告了一件事，并不会因此直接变成所有人都能读取的项目共识。

同一个知识对象的修订不能暗中改变 `scope`、项目或私有会话。明确共享需要经过相应业务授权并单独建立共享记录；本包没有自动把同事私聊转为共享知识的流程。

CLI 导入 `private` 内容时使用的 `tenant_id`、`app_id`、`actor_id`、`chat_id`、`thread_id`，必须与实际使用该内容的可信会话一致。用一个临时聊天 ID 导入，之后换成另一个 ID 查询，会被隔离规则挡住。

## 4. JSONL 文件长什么样

JSONL 是每行一个完整 JSON 对象，不在外层包数组。每条最多 64 KiB，`content` 最多 20,000 个字符；默认一次最多处理 1,000 条非空记录。超限或格式错误会按行报告。

文件顶层只允许这些字段：

| 字段 | 是否必填 | 含义 |
| --- | --- | --- |
| `item_key` | 是 | 稳定的条目标识；同一条知识更新时继续使用原值。 |
| `kind` | 是 | `business`、`rule`、`fact`、`case`、`style` 之一。 |
| `content` | 是 | 完整内容，保留必要条件、例外和证据状态。 |
| `source` | 是 | 来源对象，必须包含非空 `uri`、`observed_at`；可补充 `version`、`title` 等来源信息。 |
| `scope` | 否 | 默认 `private`。 |
| `project_id` | 视范围而定 | `project` 范围必须填写；`tenant` 范围不能填写。 |

`observed_at` 建议使用带时区的实际读取或确认时间，例如 `2026-10-30T09:00:00+08:00`。来源修订号放在 `source.version`；它与知识库内部递增的记录 `version` 是两回事。不要把猜测的时间写成已确认的业务时间。

### 两个合成示例

现成文件为 [examples/knowledge.example.jsonl](examples/knowledge.example.jsonl)，两条都明确是合成资料。

```jsonl
{"item_key":"sample.delivery-evidence","kind":"rule","scope":"tenant","content":"合成示例规则：交付确认需要核对本次约定的验收证据；尚未取得的材料明确标记为待核。此条仅用于演示导入，不代表任何公司的现行制度。","source":{"uri":"synthetic://examples/delivery-rule","observed_at":"2026-10-30T09:00:00+08:00","version":"example-1","title":"合成验收规则"}}
{"item_key":"sample.clarify-dependency","kind":"case","scope":"private","content":"合成沟通案例：对方说某个物料晚到，处理者先核实物料是否影响下一项测试，再确认可继续推进的准备工作。案例结论：尚未核清依赖时，不直接把风险报告写成确定延期。","source":{"uri":"synthetic://examples/dependency-case","observed_at":"2026-10-30T09:00:00+08:00","version":"example-1","title":"合成依赖核查案例"}}
```

第一条展示共享工作原则的写法；第二条展示私有处理案例的写法。两者的 `item_key` 不相同，类型与可见范围也独立保留。正式补充公司知识时，用你实际提供的资料与来源替换合成内容，不把示例当作已经批准的公司制度。

**知识文件不携带身份或权限。** 不要在 JSONL 顶层加入 `tenant_id`、`app_id`、`actor_id`、`is_owner`、`owner_ids`、`allowed_project_ids`、`approve`、`status` 等字段；这些字段会被拒绝，而不是用于改变执行身份。

## 5. 由本机管理员准备可信配置

配置样例为 [examples/import-config.example.json](examples/import-config.example.json)。其中 `REPLACE_WITH_...` 都是明确的占位值，CLI 会拒绝直接使用。复制样例后，必须用现有系统已经核实的身份与权限配置替换，不能用显示名称代替固定 ID。

从本包根目录操作：

```bash
cp examples/import-config.example.json examples/import-config.local.json
```

配置要点：

- `owner_ids` 是当前 `tenant_id`、`app_id` 下可信 owner 的 actor ID 数组。`is_owner` 由程序根据名单推导，配置文件不能直接填写它。
- `allowed_project_ids` 是当前身份、当前会话允许使用的项目 ID 数组。没有项目权限时使用空数组；不要保留占位 ID。
- `all_projects` 为布尔值，样例保持 `false`。
- `thread_id` 需要与实际会话一致；无线程时为空字符串。
- 样例 `database` 为 `../var/am-knowledge.sqlite3`，相对配置文件目录解析。配置保存在 `examples/` 时，它对应本包根目录下的 `var/am-knowledge.sqlite3`。
- 接入原 AM 时，运行服务必须读取同一份知识库。只向另一个本地文件导入，不会让原机器人自动获得内容。

这份配置属于本机管理员提供的可信运行输入。不能把同事随消息上传的配置文件当作权限依据。配置中不需要 Qwen、飞书或其他服务的凭据。

## 6. 先预检，再导入候选

以下命令从本包根目录运行。

### 只读预检

用两个合成示例检查配置和文件格式：

```bash
env PYTHONPATH=src python -m am_conversation import-knowledge \
  --config examples/import-config.local.json \
  --file examples/knowledge.example.jsonl \
  --namespace example-learning \
  --dry-run
```

新数据库路径会在内存中模拟，不创建目标文件或父目录。已有数据库通过只读连接备份到内存后模拟，不修改原知识记录。输出中的 `planned` 是计划数量；`would_create`、`would_update` 不代表已经写入。新记录的 `record_id` 为 `null`，不能拿计划编号去批准。

预检也会校验权限。加上 `--approve --dry-run` 可以检查这批内容是否具备批准条件，但不会实际批准。

### 正式导入为候选

把实际准备的资料保存为 `examples/knowledge.local.jsonl`，核对可信配置。若沿用样例数据库路径，首次实际导入前创建目录：

```bash
mkdir -p var
env PYTHONPATH=src python -m am_conversation import-knowledge \
  --config examples/import-config.local.json \
  --file examples/knowledge.local.jsonl \
  --namespace company-work
```

不加 `--approve` 时，新增内容的状态是 `candidate`。它已保存，但不会进入普通已批准知识检索。

命令始终返回结构化逐行报告。优先查看：

- `ok`：本次处理是否没有错误并完整读到末尾。
- `counts.errors`：失败条数。
- `results[].line`、`item_key`、`error`：哪一行、哪一条、因为什么失败。
- `results[].record_id`、`version`、`status`：实际保存的记录与状态。
- `warnings`：例如旧内容未重新生效、同内容的新来源信息未覆盖原始来源。

每行独立提交。某一行失败时，前后其他有效行仍可能已经成功，因此不能把非零退出码理解成“整份文件全部回滚”。有逐行错误时退出码为 `1`；配置或数据库等整体错误为 `2`。

## 7. 明确批准以后才生效

### 通过文件批准

将已逐条审阅的条目保留在单独文件，例如 `examples/knowledge.reviewed.jsonl`，继续使用同一个 `namespace` 和原 `item_key`：

```bash
env PYTHONPATH=src python -m am_conversation import-knowledge \
  --config examples/import-config.local.json \
  --file examples/knowledge.reviewed.jsonl \
  --namespace company-work \
  --approve
```

相同内容不会重复生成版本；已有候选会尝试按其确切版本批准。`--approve` 是对本次文件中每条有效内容的明确批准请求，仍要通过 owner 校验。部分批准失败时，其他行可能已经成功，必须看逐行结果。

### 通过已接入的对话链路批准

当前 engine 在成功整理出 `propose_knowledge` 候选后，会显示内容、适用范围，以及包含真实记录 ID 与版本的批准命令。

目前仍需要使用这条精确命令：

```text
批准知识 <实际32位记录ID> v<当前版本号>
```

尖括号内容只是语法说明，发送时直接复制候选预览给出的真实整行，不保留尖括号。例如，预览若给出某个真实记录的 `v2`，就批准该记录的 `v2`，不能继续使用旧版编号。

“可以”“记住了”“确认执行”等普通回复，目前不等同于知识批准。`确认执行` 属于外部动作的另一套确认流程。这个版本尚未把所有自然表达都接成可验证的知识批准指令。

批准不会改变原可见范围。私有候选仍必须在对应可信身份与会话中处理；owner 不能通过知道一个同事私有记录的 ID，就跨会话读取或批准它。

## 8. 更新规则时会发生什么

同一 `tenant_id`、`app_id`、`namespace` 下，`item_key` 标识一个持续维护的知识对象。

| 操作 | 结果 |
| --- | --- |
| 原 `item_key`、原内容再次导入 | 不重复建立知识版本。 |
| 原 `item_key`、内容发生变化 | 新增候选版本。旧批准版本继续参与检索。 |
| 明确批准新候选版本 | 新版生效，旧批准版本变成 `superseded`，保留内容与来源历史。 |
| 新候选被拒绝 | 不替换旧批准版本。 |
| 重新导入已经出现过的旧内容 | 不创建重复版本，不自动恢复旧规则；报告历史内容警告。 |
| 同一内容只修改来源时间或来源修订号 | 不假装原内容已重新核实；保留原来源并给出提示。 |
| 用原 `item_key` 改成其他范围、项目或知识类型 | 拒绝，要求先明确这是不是另一个知识对象。 |

若需要记录独立的新证据，可以单列新的 `item_key` 并说明与原记录的关系。若需要明确恢复一条历史规则，应由接续端按版本治理流程创建并审阅新的修订，不能假定重新导入旧文件就会回滚当前规则。

## 9. 怎么判断补充的知识是否真的有帮助

每次先补少量内容，再拿真实但经过必要脱敏的情境检查：

1. 它是否读取了正确项目、正确版本的来源。
2. 它是否抓住你认为最影响下一步的问题。
3. 它有没有把报告、核实、批准、执行混成同一状态。
4. 它是否按照你确认的表达偏好简洁回复。
5. 它是否在缺少证据或授权时准确停在相应边界。

如果回答不合适，先判断是资料缺失、资料过时、检索没有命中、适用条件不清，还是模型没有正确使用工具。分别修正对应部分，不把每个问题都归结为“再塞更多文档”。

本包提供可追溯的保存、检索、版本与批准机制。真实 Qwen 能否稳定理解这些资料、原 AM 能否正确调用，以及工作沟通是否接近你的预期，仍需在接入后的实际情境中验证。
