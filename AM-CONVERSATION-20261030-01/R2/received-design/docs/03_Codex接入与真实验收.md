### 必须准确理解当前能力

本轮生产模式是 **完整等价业务句式的选择与分组**。宿主提供带来源与作用域的事实合同，原 Qwen 最多调用一次，只返回合法事实 ID、句式下标和分组。程序不接受任意自由 `text`。

默认旧台账适配器只处理单项目、单字段、没有尚未合并来源的明确查询；人员职责可作有限结构化。任意进展原文仍保留完整条件块，日期/待办可能关联的进展前提也保留。`source_projection` 和 `not_covered` 都不能计为自然表达成功。

用户主动询问“资料采集时间”“来源”“快照版本”等溯源问题时，字段编译器应旁路，交回原已授权回答路径。此时保留回答所需的时间、来源和技术标识，不能把“采集时间”误解为项目关键日期，也不能把普通业务回复隐藏冗余技术信息的风格规则用于删除用户明确索取的证据。

因此，**不得把“谁负责、进展、日期、待办”四类问题的自然摘要称为已经全部实现。** 对未覆盖场景，应记录实际输出和缺口；需要扩大事实编译覆盖时，在本 R2 范围内做有来源依据的增量实现，或准确回传未完成项，不用自由截断或删除条件换取通过。

### 2. 先只读预检，再隔离合并

以下命令均在解压后的包根目录执行；`python3` 应替换为本机原工程使用的 Python 3.12 解释器。

```bash
python3 integration/install.py --target-root /实际原工程绝对路径 --dry-run
```

安装器默认就是 dry-run。若出现 `HOST_CHANGED_MANUAL_MERGE_REQUIRED`，说明当前文件与补丁固定基线不同，应阅读差异并手工局部合并。**不得 reset、checkout 旧提交，或用 `integration/patched/` 整文件覆盖来通过检查。**

只有隔离副本与精确基线完全匹配时，可验证安装器的实际应用：

```bash
python3 integration/install.py --target-root /实际隔离副本绝对路径 --apply
```

对较新的工作树，按 `host_changes.json` 的修改意图手动合并，并记录最终差异。安装器不会修改配置、迁移业务库或重启服务；不要把 `--apply` 成功称为原服务更新成功。

接线必须位于**普通只读回答的原事实检查之后、`_finish` 持久化之前**。最终文本进入原 `finish_event`，使 `reply_json` 和 assistant history 同事务保存；既有显示层仍可能按原规则替换短语，因此必须另外核对最终回复与实际 `rendered_text`、出站正文的绑定。不能在 `display` 或发送以后才另加无记录的重写。

### 4. 真实 Qwen + 合成业务事实探针

这一层验证模型接口、受约束输出质量、模型排队与额外耗时，不使用真实业务资料，也不调用飞书。

脚本提供 `--factory module:function` 注入点。Codex 必须依据当前宿主提供一个**复用原协调器的工厂或受控代理**。如果原协调器只存在于运行进程内，应在该进程的既有受控入口内执行探针，或实现只转发到既有协调器的本机测试适配；不能为使脚本跑通而新建第二个 `ModelCoordinator`。包内没有假定或虚构本机启动模块，工厂接线是本机待补事项。

确认工厂指向既有资源后执行；下面的模块名是待替换占位符：

```bash
python3 scripts/evaluate_live.py \
  --run-model \
  --factory 实际宿主模块:取得既有协调器的函数 \
  --output verification/live-qwen-R2-01.json
```

可先定向执行四个基础案例：

```bash
python3 scripts/evaluate_live.py \
  --run-model \
  --factory 实际宿主模块:取得既有协调器的函数 \
  --case Q01_people --case Q02_progress --case Q03_dates --case Q04_todos \
  --output verification/live-qwen-four-R2-01.json
```

脚本使用 `src/am_reply/examples.py` 中 14 个合成案例，故意包含保护回复与原文投影；这些案例不会都调用模型。`requested_model_calls` 记录尝试次数，不保证全部完成推理；应另从原协调器记录区分实际启动、完成、忙、暂停、超时和未知结果。

脚本使用合成 scope、合成 source version 和空测试 guard，**不能证明真实身份校验、来源撤权或飞书投递通过**。脚本结果保留 `human_review_completed=false` 和 `style_acceptance_passed=false`，人工评价完成前不得手动改成 true。

### 5. 补齐三路对照评价

对同一问题、同一份冻结的事实合同保存三路输出：

- A：原普通回答；
- B：`am_reply.contracts.fallback_text(contract)` 形成的固定自然句式；
- C：本轮 LLM 选择与分组后，通过程序和原宿主检查的最终候选。

`evaluate_live.py` 已分别记录 `before`（A）、`fixed_baseline`（B）、`candidate_after_checks`（通过程序检查的 C）和 `after`（本次最终采用值）。C 为空表示没有可用于评价的已通过候选；模型失败后的 B 路回退不能冒充 C 成功。脚本不自动完成三路人工评价。Codex 应在受控评价中随机交换展示顺序，请所有者比较直接性、自然度、接近本人程度和信息完整性。保护回复的 B 值为空，不参加润色胜负统计。

如果 C 与 B 完全相同，标记相同；如果 C 没有更自然或更好理解，不能仅凭一次模型调用就报告收益。可以对这类场景采用 B，减少额外等待，同时把事实如实写入验收结论。

### 6. 原宿主受控 shadow

在已有获准范围内，把配置从 `off` 调成 `shadow`，使用正常入口处理真实授权的查询。`shadow` 可产生候选，但实际保存和发送的仍应是原回复。

原指标只记录 disposition、原因、耗时、指纹与长度，**不包含候选正文**。需要做表达对照时，使用本轮受控的临时评价记录器观察 `RewriteResult.candidate_text`，绑定具体事件、当前权限和原资料有效期；不要声称现有计时指标已经保存候选全文，也不要新增无限期生产聊天日志。

在此阶段核对合同来源、范围、scope、source version、主模型与表达模型的调用次数，以及最终历史和出站内容。源访问或取消守卫失败时，候选和旧回退文本都不能继续投递。

### 7. 已获准范围内定向 enforce

只有合成检查和真实模型探针符合本轮门槛后，才在原已获准测试对象与用途内定向 `enforce`。首先验证本人私聊，再验证已获准的第二位用户或测试群场景；全部门启用不作为默认动作。

本机服务更新由原协调方统一执行，核对实际加载文件与最终源码，不另起消费者。原 Qwen 不因本次表达节点切换而重启。保留更新前后的配置、实例锁、消费者数量和受保护业务记录证据。

实际测试从正常问句发起，包含桌面和手机。客户端发出的测试查询、收到的最终回复、历史、事件结果和飞书读回须关联到同一事件；仅在控制台看到候选不算投递验收。

| H23 | S/H：重放、发送失败后恢复、进程重启 | 已完成事件复用同一最终正文，不再次调用模型或执行业务；历史、reply_json与出站一致 | 同一事件多次处理、调用数与正文哈希 |
| H24 | H/U：本人桌面/手机、已获准第二用户及群私聊范围 | 格式可读，无截断；候选、风格资料和事实不跨人/项目/群范围复用；必要区分信息在手机仍可读 | 每个子场景单独记录身份范围、客户端与最终回读 |

H15—H23 中危险变化优先在隔离副本与受控故障注入中验证；不得在正式业务中制造权限事故、重复发送或异常审批来取得证据。真实环境可只读核对同一守卫和入口的接线，再在已有授权的测试对象上补必要集成证据。

## 五、验收口径与指标

### 1. 必须满足的正确性条件

- 所有纳入本轮人工核对的最终回复，关键事实、责任关系、日期含义、否定与条件 **零漂移**。这里指已核对样本的结果，不是对所有未来输入的数学保证。
- 台账资料保留简短的“按现有记录”限定；读到资料不等于独立核实业务。代码通过 `require_record_attribution` 强制这一点，不能把删除技术噪声扩大成删除证据状态。
- 原文请求、待确认预览及事务回复按保护要求不变；未获批准的外发、写入或挂载次数为零。
- 用户主动索取来源、采集时间或版本时，正确回答其溯源问题并保留所需已授权技术信息；不得以拟人化为由删掉这些内容。
- 同一已完成事件不重复调用表达模型；任何单次正常表达尝试最多调用一次。
- 撤权、取消和过期场景不能发送旧候选或旧回退文本。
- 原历史、事件结果与实际出站使用同一最终正文；使用不同展示文字时必须沿用明确、可核对的原版本绑定。

任一关键正确性失败都应停止对应范围的 `enforce`，回到 `off` 或仅保留不影响业务结果的隔离检查，修复后定向复验。

### 2. 自然度与收益：以下均为建议阈值

建议先在四类常见问题各收集至少 10 个实际样本，总计至少 40 个；可以使用已有获准来源和合成事实，不需要为采样扩大用户范围。样本不足时也能给出初步结果，但应标样本量和不确定性，不能据少量样本宣称稳定 p95 或全量效果。

建议使用1—5分：直接性、自然度、接近本人程度、信息完整性分别评价。普通自然表达样本的自然度均分建议至少4分；C相对B的盲选偏好建议超过60%，并单列相同和无法判断。阈值是本轮建议，不是用户已确认的硬性产品指标，也不是研究文献给出的标准。

如果 C 未优于 B，应如实记为“额外 LLM 收益未证明”，优先改善候选、缩小调用范围或采用固定优选句式；不能把字数减少当成全部自然度收益。

### 3. 覆盖率必须公开分母

建议至少同时报告以下指标：

| 指标 | 分母与分子 |
|---|---|
| 合同形成率 | 四类普通查询中形成有效可信合同的次数 / 四类全部查询次数 |
| LLM表达覆盖率 | 实际进入表达且候选最终被采用的次数 / 四类全部查询次数 |
| 模型候选接受率 | 合法并被宿主采用的候选数 / 实际表达尝试数 |
| 原文投影比例 | `source_projection` 次数 / 四类全部查询次数 |
| 未覆盖比例 | `not_covered` 或宿主投影不可用次数 / 四类全部查询次数 |
| 质量达标覆盖率 | 事实与自然度均通过的最终回复数 / 四类全部查询次数 |

按人员、进展、日期、待办分别列出。`source_projection`、`not_covered`、宿主二次拒绝、超时回退都不计入 LLM自然表达成功；不能只挑人员查询为分母后宣称四问整体通过。若进展/日期/待办仍未获得足够自然表达覆盖，本轮可报告限定范围通过，但用户原目标仍为部分完成。

### 4. 时延与原资源保持

报告原回复与新增表达后的端到端时间、模型排队、主推理、表达推理和投递时间，并给 p50 / p95 与样本量。`max_seconds=6.0` 仅为初始配置上限，不是实测耗时，也不说明原三秒体验目标已经通过。

核对原模型身份及摘要、原协调器/消费者、配置、实例锁、600秒身份和 `ledger_write=false`。加载文件数量按真实新增文件统计，不机械沿用上一轮“125份”数字。

## 七、失败与回退

遇到关键事实漂移、历史与发送正文不一致、确认绑定变化、权限守卫失效、重复动作或原资源被绕过，立即停止相应 `enforce` 范围。优先把 `output_rewrite.mode` 恢复为 `off`，由原协调方按既有方式统一更新原服务，并核对原功能恢复。
