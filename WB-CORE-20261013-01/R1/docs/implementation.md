# WB-CORE-20261013-01 / R1 实现与运行说明

## 一份业务状态

复用原 SQLite LocalStore、sources.workItem、receipts、audit、reminderRun、followupNotification 和助手会话。没有另建事项库、消息库、平行助手或模型服务。

workItem.core 补充候选纳入、基准等级及人工来源、当前需要、责任步骤、有效处理证据、提醒轮次、临时等级、暂停、延期通知、检查覆盖、真实依赖和协作准备。原 P1 时间、进展、风险结论和历史继续使用。

输入原件保存在既有来源集合，记录事件与采集时间、作者、原图次序、引用身份和处理阶段。文本引用逐字核对，图像观察绑定实际读取的原图；AI 输出不冒充原始证据。保存、发送、回读和业务完成分别表达。

事项入口、全局助手和飞书引用回复调用同一 P1 操作与核心处理函数。事务执行版本、依据和幂等检查；旧分析不能覆盖较新编辑。同一请求查询原回执，重复原图不重复落账，同图的新指令继续处理。全局入口逐事项携带同样的时间规则。

## P1 与纠正

保留普通保存回列表、混合输入留场、只设时间提交、缺时间先保存、检查日期默认北京时间10:00，以及完成日期的原精度和次日边界。

同次提交的相关事项分别记字段补丁，整次撤销在一个事务中核查所有冲突；冲突不产生部分撤销。新建事项撤销后保留有效历史身份并撤下关注，不删除必需字段。原件、历史批准与已发送事实保留，纠正改变的是原输入对当前判断的效力。随后复核提醒、临时等级、风险与未执行动作。

## 跟进与运行

可核验成功回执才计数，电脑排队不算展示。双渠道同轮至多一次；迟到回执不覆盖新的等级、暂停或关闭。第三次有效提醒同一需要最多升一级，最高P1；清零、跨天和暂停恢复不额外取得升级机会。

实际行动、实质进展或可执行安排可以清零；妥善处理且有有效后续时间，或明确无需本人介入，才暂缓常规催办。“收到”“在处理”和只改预测不自动满足条件。P0正式等级须本人决定，全力处理后仅实质变化、明确检查和新决策需要通知。

日历是有来源、版本和适用期的逐日配置，缺日期返回缺口，不默认双休。普通通知18:00后或休息日延期，延期意图持久保存，发前重新核对。明确检查和真实紧急介入保留例外。恢复只处理当前需要，不回放全部漏发时点。必要重试仍读不到的明确检查会报告“尚未核实”，不计催办次数。

本地失效复核一直有效，不依赖外发开关：来源撤回、交付变化和前提失效会更新原事项及待发状态。周期检查、模型分析和真实通知由工作区持续跟进设置控制，默认未启用。没有恢复既有暂停的外部任务。

## 依赖、资料和协作

依赖引用两个稳定事项及原文。时长范围存在、范围已共享、计划确认节点、当前剩余时长、有效窗口和协调结果分别核查。最长超窗不直接判延期；最短超窗由本人协调；确认协调无效则准备影响共享；相关人知晓但安排未定时准备本人向领导说明的材料及候选方案。其他有依据的关闭窗口也可提示，不把单一阈值泛化。

交付准备基于实际交付物和节点，整理适用模板、资料和缺口。责任人编写、关联并推动审核，不增加内容验收、不代关联或改共享。有效关联和“已审核”从实际业务字段读取，模型给的类似值不能替代。未知节点、要求冲突和模板不明分别交本人判断；提供方和所有者明确时准备对应消息。

第三方消息在原助手入口集中预览，完整展示收件范围和正文，逐条改、取消，批准选中项。不同报告分开发。候选纳入与消息批准分别落账。发前重查来源、接收身份、关联和必要性；无必要停止对应未执行项，实质变化重新预览。明确未发出的失败按原批准重试，未知先查。人工接手只作用于具体消息，服务恢复不自动交回。

飞书输入位于既有事件桥之后：先回读来源和发送人，再关联旧提醒、读取最新事项并调用原助手。本人回复可自动返回实际处理回执；同事的新同步消息仍预览。缺映射时保留输入并提供目标消歧，接收、理解、保存、回执发送状态独立。

## 模型、隔离和恢复

复用既有 Codex、检索、图片解析、运行设置、预算和用量回执。简单记录走输入/事项职责；存在业务对象或相关请求时才增加依赖/资料职责。不换模型、不另起子代理。

复杂请求分两段：先保存已核对的输入事实与安排，再用收窄的对象和原文引用进行依赖/资料准备。后一段不携带整段会话和全量编辑协议；共用引文编号，避免反复复制同一原文。后段失败、取消或超时会明确报告未完成范围，不抹去第一段实际保存，也不伪报准备完成。

所有本轮写入验证使用独立目录、端口、模拟工作区和适配器。正式数据库不作为测试库；真实模型仅从正式设置只读取得 Astra/max 和50万后台额度，随后配置到隔离库。没有复制正式业务原文。

新增状态随原备份持久化。恢复副本保留历史和未知执行事实，撤销待执行批准，不重放旧发送；替换恢复后持续跟进保持关闭。原节点、Tasks、会议和专业审批仍有独立语义。

## 真实验证边界

已只读确认飞书空间、类型和交付审核字段，并读取三个候选测试项目。具体主链载体待唯一选择；真实第三方发送仍需具体收件范围和完整正文的批准。无消息ID且真实通道不支持按原请求键查询时，状态保留未知，不重发。

正式安装、生产迁移、真实调度启用、产品源码push/merge、GPT独立审计和用户验收均未由本轮代码或审核上传推定。未声称覆盖所有专业质量风险或全自动排程；更广Tasks、会议、上传归档继续沿原能力。


## 本轮验证中修正的关键问题

- 原模型把时长范围已共享混为风险影响已知晓。现在只有明确的影响知晓依据才能进入“找领导推动决定”，保留原失败与真实输出重放。
- 复杂请求曾在单次组合输出中超时。输入职责已移除无关通用编辑协议，依赖/资料职责使用有界上下文和共用引用编号。max/ultra沿用原设置，单阶段等待上限为10分钟；普通设置为4分钟，测试可显式覆写。复杂样例仍有明显等待时间，不承诺日常固定耗时。
- 飞书CLI实读显示幂等键上限50字符，本人通知和输入回执使用稳定短摘要；只有CLI明确的发送前校验失败才认定未发出，其余不明错误保留未知。
- 同事回传计入后台预算；排队、跨日续办、准备阶段单独续办均保留原输入与原业务结果，不用主动对话额度绕过后台限制。
- 完成要求和检查点触发新的核实，即使来源未变也不会因有效等待而永久停查；时间变化本身不是新进展，不清零。
- 迟到指令按具体字段的较新人工决定判断。新优先级不阻挡无关检查安排；旧检查指令不能覆盖后来检查时间，普通反馈仍保留。
- 发前通过既有飞书同步适配器只重读相关已登记目标和节点。读取失败不能证明无必要，也不能使用旧镜像直接发送。
