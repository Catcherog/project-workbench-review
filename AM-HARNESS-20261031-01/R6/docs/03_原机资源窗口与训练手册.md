# 原机资源窗口与训练手册

## 1. 要回答的问题

用户希望确认：内存不足是否因为 Qwen3.8 仍在跑；后训练前能否暂时结束其模型占用，训练后恢复。

本轮开发提供只读盘点、受控诊断和训练窗口三层能力。只读盘点随时可在既有范围运行；受控诊断只临时释放已经精确绑定的原 Q8 并恢复；训练仍须满足全部原 R5/R4 条件。没有永久停用、升级、改量化或换模型授权。

推断：原 Q8 常驻值得优先调查，若真实释放量超过9.55 GiB且压力、swap及业务条件合格，资源门槛可能成立。**不能用14.449+28.461预言释放后的available**。RSS有共享／映射等含义，训练还需要稳定运行余量；最终判断来自实际测量和原R4。

## 3. 只读盘点

合入后，在原工程的 `am-integrated-r6/` 目录运行：

```bash
python3 -m am_training_window.mac_probe snapshot --output /absolute/private/window/before.json
```

探针仅执行固定的只读系统命令，记录实际页面大小、内存页面、压缩、swap、压力、进程名和RSS，不收集完整命令参数或环境变量。非Mac明确返回unsupported，不生成看似Mac的伪数据。

同时由Codex在原机只读确认：

1. `/api/ps`对应的真实服务、模型、digest、runner、context及管理器配置。
2. 精确Q8 worker的PID、父进程、启动时间、监听关系与原模型文件；防止同名进程或PID复用。
3. 原消费者唯一性、原锁真实路径及inode、当前配置指纹。
4. 所有业务入口与队列：Harness任务、原tasks、AM conversation、普通私聊另库、信息提取／群查询等；queued及processing均不能漏计。
5. 可安全停止并恢复原模型的本机管理器接口；只终止worker时，兼容metadata服务是否继续可用。

本包没有硬编码`killall`、模糊进程名或SIGKILL。优先使用实际原管理器的卸载／休眠及恢复能力。若确需结束精确worker，只能在已绑定身份、无在途业务、恢复步骤和管理器行为均已核验的受控窗口中进行。未提供的本机控制源码不能用云端假端口替代。

## 4. 诊断窗口：不依赖独立测试，不启动trainer

调用 `TrainingWindow.diagnostic()`，该入口没有trainer参数。

1. fresh检查原模型、配置、metadata、唯一消费者与业务状态，创建私有0600 journal。
2. CAS占用`resource_window_owner`，只阻止新模型claim。已有多步任务继续完整结束；新消息留在原received/queued；所有任务attempts及终态保留原义。
3. 有界排空整个业务任务，而不只等某一次模型调用结束。仍有pending/active时，撤销本窗口owner，保留业务原状态，不设置provider_pause、不卸载模型。
4. 排空后seal原provider_pause，在原协调锁内再检查空闲，写入可恢复的卸载意图，再调用精确lifecycle.suspend。
5. 核验原模型不再驻留、metadata可读，记录原R4口径available、压力、swap、pending和进程变化。`mac_probe`估算页面字段只辅助解释，不替代`psutil.virtual_memory().available`。
6. 重新取得同一原锁，恢复同模型/digest/context及配置；核验服务与消费者后CAS释放本窗口pause/owner。其他暂停原因如STOP_UNKNOWN不能被清除。
7. 保存前后与恢复快照、阶段耗时、错误、诊断trainer_attempts=0。可用量不够也完整恢复，留下具体结果。

比较命令：

```bash
python3 -m am_training_window.mac_probe compare /absolute/private/window/before.json /absolute/private/window/after-unload.json --output /absolute/private/window/delta.json
```

必须额外记录恢复后快照。单独前后比较不等于模型或业务恢复成功。

## 5. 训练窗口：两次门禁，原R4仍掌握资源放行

`TrainingWindow.train(fresh_r5_gate, execute_original_r5, trainer_stopped)`按以下顺序工作：

1. **停Q8之前**调用原R5 fresh gate。独立材料缺失、声明失效、原件不可读、计划变化等立即以具体原因阻塞；此时不扰动原模型。
2. 完成与诊断相同的准入、排空、精确停载和观测。
3. 退出维护阶段的原锁，同时保留维护准入标记；再次读取真实R5输入绑定，与前次一致才继续。
4. 实际启动回调重新执行原 `pilot-execute --plan … --execute`。**不可重放之前算出的R4 argv**。即使两次检查间材料未变，原R5执行入口仍做最后门禁。
5. 原R4的fit／reload各自进入原`OriginalLease`；锁内按原24 GiB启动、5 GiB运行底线、swap增长1 GiB及原压力／业务抢占规则执行。所有训练超参继续读取既定计划与原manifest，未经授权不调低策略或缩小任务冒充原计划。
6. 原fit工作者退出和进程组停止确认后才进入原reload。新业务来到时保留原队列可见性，由原R4让路，不丢任务、不改业务终态来维持训练。
7. 所有训练工作者停止被独立确认后，再恢复原Q8。仅命令返回、超时、某个PID消失都不足以证明整组停止；停止不确定时保留maintenance和recovery_required。

原R4允许`loaded_models=[]`，所以无需修改模型身份保护。但原R4会读取`127.0.0.1:11434/api/ps`；若把整个兼容metadata服务停掉，训练资源检查将阻塞。这也是必须精确释放模型worker的原因。

外层不能持有原非阻塞flock再启动R4；否则R4子进程无法拿到同一锁。维护短锁→释放→R4原租约→恢复短锁的顺序已在代码和合同中固定。

## 6. 异常恢复

| 情况 | 必须行为 |
| --- | --- |
| 门禁缺失／变化 | 记录具体R5原因；不启动trainer；已停载则恢复原Q8 |
| 业务忙或排空超时 | 不停止模型；释放本窗口owner；保留队列与原运行任务 |
| 部分卸载失败 | 依journal恢复意图重建原模型，不能假定无副作用 |
| 训练异常／取消 | 先证明fit/reload全部停止，再恢复Q8 |
| 停止未知 | 不叠加加载Q8；保持准入封闭，明确recovery_required |
| 恢复失败／身份不符 | 不开放准入；保留具体恢复阻塞 |
| journal写入失败 | 尝试恢复；不能因日志异常跳过恢复工作 |
| 放开准入后崩溃 | recover幂等核验已恢复状态；不能错误再暂停或续训 |
| 外部pause出现 | 不覆盖／清除其他暂停原因；保护原协调器状态 |

`recover()`仅恢复原服务，不自动重新训练。恢复证据应包含模型身份、配置、metadata、消费者和业务队列，不只HTTP存活。

## 7. 必须回传的资源结论

分别回答以下六问，并附真实前后时间与来源：

1. 占用最大的进程是否精确属于原Q8？是否还有其他主要占用？
2. 临时停载后实际available增加多少；是否达到24 GiB且稳定；压力和swap怎样变化？
3. metadata是否保持可读；未因普通请求自动唤醒Q8？
4. 维护期间新消息与取消如何处理，所有pending是否仍被原R4看见？
5. 同模型及配置是否成功恢复，恢复耗时与真实业务健康如何？
6. 若资源足够，独立材料及其他R5条件是否同时满足？只满足资源不得宣布可训练。

报告可以得出“释放Q8后资源可用”或“仍不足／窗口不安全”，不能把诊断结果写成已训练、效果通过或已上线。
