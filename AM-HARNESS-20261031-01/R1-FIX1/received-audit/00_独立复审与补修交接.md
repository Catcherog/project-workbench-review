## 3. 五项需修复问题

### F01 / P1：停止已生效，普通本地业务变更仍提交

复现先登记合成跟进，再暂停至 `version=2, paused=1`。用户要求恢复；在 `ActionItems.change` 业务事务开始之前，经原入口处理“停止当前任务”，随后继续原 handler。

实际：任务 `cancelled`，worker 返回 `stale`，跟进却变为 `version=3, paused=0`；该任务没有 reservation。任务结果被抑制，已取消要求仍改变了业务状态。

根因：`change_followup` 注册为 `effect=local`。`ConversationAgent` 对 local 工具直接调用 handler；`action_context` 只在 external executor 中绑定。于是虽然 `ActionItems.change` 调用了 `reserve_effect`，它仍因 ContextVar 未绑定而直接返回。后置 `after_tool` 检查已经晚于业务写入。

依据（相对原工作区）：

- `am-conversation-r1/src/am_conversation/engine.py` 365–412 行。
- `am-conversation-r1/src/am_conversation/business.py` 293 行。
- `FS-AGENT-GROK-POC-20261017-01_R1_Studio/src/am_harness/reservation.py` 12–45 行。
- `FS-AGENT-GROK-POC-20261017-01_R1_Studio/src/fs_agent/action_items.py` 80–104 行。
- `local-qwen3.8/feishu-bridge/am_harness_host.py` 326–329 行。

修复标准：所有实际改变状态的 Harness local 工具都必须绑定当前 run/revision/cancel_epoch/generation，并与实际业务提交形成明确的取消顺序。同库写入在同一事务检查；跨库路径明确占用、提交记录及中断对账，不能声称跨库原子。Harness 任务中缺绑定不得静默视为普通 legacy 调用。普通跟进登记/暂停/恢复仍保持原无需新增批准的交互。取消前已经完成的真实变更继续保留。

已实测范围为 `change_followup.resume`。对 create_followup、control_reminder、反馈、工作笔记及其他 local 写入做定向检查，不把未实测操作写成已证实受影响。

### F02 / P1：正常送达的回答在下一轮模型提示中消失

第一轮回答已经 `sent + verified=1`，原输出记录也为 `acknowledged`；`FencedHistoryStore.history` 可以读到它。用户再问“把你上一条回答展开说明”，捕获第二轮真正送给原 JsonProvider 的 prompt，却不含上一轮回答。

实际标识：原消息 `om500`，内部事件 `harness:run_…:v1`。`host_context.py` 用内部事件查询 `am_conversation_outputs.event_id`，而 `LegacyConversationBridge.enqueue_reply` 向该列写入的是真实 inbox 消息 ID。查询不命中后，正常回答被过滤。

依据：`am_harness/host_context.py` 52–82 行；`am-conversation-r1/src/am_conversation/legacy.py` 397–415 行；`am_harness/history_adapter.py` 41–98 行。

修复标准：建立真实来源事件、内部事件、run/revision 与 outbox 回执之间的确切映射，保持 scope、来源版本、权限版本、期限及已验证派送检查。历史条目应按稳定身份关联，不依赖仅按正文相等猜测。正常已送达内容可继续进入实际模型 prompt；取消、未送达、撤权、旧 revision、过期及跨 scope 内容仍须排除。

### F03 / P1：切换项目后，“那负责人呢”仍回答旧项目

顺序复现，无并发竞争：

1. “需求75的项目进展”走快查询。
2. “请分析需求76的进展并提出建议”走持久模型路径并完成。
3. “那负责人呢？”仍零模型返回需求75的 AR1测试甲。

第二步结束后，原会话 focus 已为需求76；独立 `FocusCache` 仍为需求75。快捷代词路由只信自己的 600 秒缓存，忽略刚完成的项目切换。

依据：`am_harness/fastpath.py` 136–140 行、`FocusCache` 更新路径；`am-conversation-r1/src/am_conversation/tools.py` 100–104、110–133 行；`am_harness_host.py` 182–201 行。

修复标准：以当前 scope 中有事件顺序、期限和任务版本依据的项目焦点解析代词。新项目已明确切换时更新或使旧快捷焦点失效；无法证明引用关系就回原澄清/模型路径。不要退回无期限的全局 focus。另验收长任务晚返回、取消/更正、跨 thread 与跨人场景，旧任务不得覆盖较新焦点。

### F04 / P1：模型调用前的上下文超限会隔离全局执行通道

用原存储 API 建立 3 条工作笔记，每条 2,750 字，均低于 save_work_note 工具的 3,000 字上限。随后普通复杂请求在本地上下文构建阶段产生 `MANDATORY_CONTEXT_TOO_LARGE`。

实际：模型调用数为 0；任务被记为 `unknown`，全局 Harness lane 变成 `quarantined`。再提交普通请求，worker 返回 idle，后续任务持续 queued。

根因分两处：`host_context.py` 把工作笔记等 current 状态全部塞进强制 system 内容，绕过可选整块预算选择；`TaskRuntime` 在本地准备之前就设 `runner_started=True`，此确定性本地拒绝没有被识别，进入隔离分支。

依据：`am_harness/host_context.py` 86–94 行；`am_harness/context.py` 220–241 行；`am_harness/runtime.py` 83–125 行。

修复标准：工作笔记等可选状态按完整条目纳入预算，记录省略原因。能证明尚未派发的本地预算拒绝应明确结束本任务并释放 lane；也可通过安全的上下文选择使请求正常完成。须用阶段/类型及真实派发记录证明状态，不得仅匹配任意异常字符串就释放资源。原 STOP_UNKNOWN、未知 provider 执行、lease 隔离与未知副作用继续保持原对账要求，不能自动清暂停或重放。

### F05 / P2：排队过期后静默终结，inbox 悬挂

正常入队后将合成时钟推进 121 秒，仍在内容有效期内。启用并执行完整 `am.pump()`、等待 worker/I/O，再执行维护，最终仍为：

```json
{
  "run": {"state": "expired", "error": "DEADLINE_EXCEEDED"},
  "inbox": {"state": "harness_queued", "error": null},
  "failure_notices": 0,
  "model_calls": 0
}
```

`DurableStore._maintain` 批量终结过期任务；claim 不再返回这些任务。宿主仅在 run_once 返回具体 run_id 时同步原 inbox 和通知，完整 pump 也没有补偿扫描。

依据：`am_harness/store.py` 265–274、535–548 行；`am_harness/runtime.py` 67–70 行；`am_harness_host.py` 250–259、310–316 行。

修复标准：维护导致的终态变化须形成持久、幂等的同步工作，更新原 inbox 终态与错误；在当前身份和发送期限仍有效时送达一次不含业务正文的超时说明。重复维护与重启不重复通知，不延长期限，不自动重放过期任务。期限或权限已失效时仍完成内部状态收尾，按原规则决定是否允许通知。
