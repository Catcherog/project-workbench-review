## 3. 原有误失效的原因

v1 对相关来源完整 Source.to_dict() 求摘要，其中包含轮询频率。即使原文、事实、权限和有效新鲜度没有变化，纯调度参数变化也会改变摘要。

任意来源的权限或映射变化还会推进同一个 source_access_version。文档生成、通知入队和查询投递都比较该值，因此别的项目的来源变化也会拒绝当前稿件。

修复需要同时满足：

1. 不能忽略读取身份、可见范围、分析映射、新鲜度或保留期的真实变化。
2. 不能只比较当前 ACL，遗漏撤权后恢复的历史。
3. 不能只绑定已提取事实，遗漏尚未解析的新消息。
4. 生成、提交、展示、翻页、入队和发送使用同一协议。
5. 旧稿、旧缓存和旧投递不能直接改标为 v2。

## 4. v2 证据绑定契约

新稿协议为 am-document-evidence-binding/2。旧 /1 的原状态摘要和全局来源版本守卫保留。外层共享证据契约和文稿视图协议继续使用原版本。

| 字段 | 含义 |
| --- | --- |
| schema | v1、v2 明确区分；未知版本拒绝 |
| project_id、project_code | 项目身份及业务编号，不能由模型推断挂载 ID |
| scope | tenant、app、user、chat 及空的保留维度，逐项匹配请求 |
| expires | 请求、文稿和原文期限的上界；检查只能缩短，不能续期 |
| access_version | v1 的全局守卫；v2 保留观测值，相关性由 v2 摘要决定 |
| state_hash | 当前相关业务、授权和覆盖状态的整体摘要 |
| dependencies | 相关原始对象、版本和原文期限 |
| ledger_evidence | 当前项目台账原件；失效原件不能由项目缓存替代 |
| component_hashes | v2 分项摘要，authorization 用于识别权限变化；不含业务原文 |

component_hashes 必须恰好包含 authorization、project、sources、objects、facts、quality、gaps、pending 八项。每项为 64 位小写十六进制 SHA-256；state_hash 对 schema 与这些分项重新求摘要，禁止缺项、未知项或仅保留一个无法核对的总体哈希。

信息库内部时间沿用毫秒，文稿/视图 expires 使用 Unix 秒；读取预算使用单调时钟。转换在原边界完成，不能把墙上时钟或毫秒值直接用作读取剩余时间。

### 4.1 一个信息事务中的读取集合

读取当前主体可见来源、相关项目关系、台账原件及字段一致性、当前原始对象、删除和完整度状态、原文期限、事实及语义限定、冲突、待确认、缺口及待处理集合。

台账有权威项目对象 ID，可以按项目过滤。消息等来源可能仍有未确定项目归属的内容，因此保留相关来源的整源原始对象覆盖。新消息尚未形成事实时，仍能使旧稿失效。

### 4.2 稳定策略投影

仅排除已明确识别的采集调度参数。未知 settings、读取身份、分析规则、原文保留期等仍保守进入摘要。

原事实逻辑在没有有效显式 freshness_seconds 时使用 max(120, poll_seconds * 2)。因此，纯 poll_seconds 变化只有在有效新鲜度不变时才可继续。v2 的返回信息、质量判断和摘要必须使用一致的新鲜度解释。

轮询时间戳、租约时刻和重试次数本身不是新依据；原文版本、待处理集合、缺口集合和实际陈旧状态变化仍须重新核验。

### 4.3 单调权限与项目成员版本

当前 ACL 和相关来源的持久权限版本一起参与 authorization 摘要。撤权后恢复时，配置看似相同，但版本已推进，旧绑定仍失效。

共享台账的项目成员变动按当前项目判断。无关项目增删不改变当前项目的成员版本；当前项目移出后再移回则推进版本。未能证明无关的范围变化继续保守拒绝。

版本元数据包含数据库命名空间、全局版本水位和保守回退版本。若旧 writer 更新了全局版本，却没有同步文档权限版本，不能推断它与当前项目无关。捕获、重新打开和后续写入需保留这次未知变动造成的失效。

新增表及事务规则：

| 表 | 持久字段和职责 |
| --- | --- |
| document_access_meta | singleton 主键；namespace、access_namespace、access_revision、fallback_epoch，绑定文档历史和全局水位 |
| document_source_access_epochs | source_id 主键；revision，保存来源级撤权/可见范围历史 |
| document_project_access_epochs | source_id + subject_id 联合主键；revision，保存项目成员移出/移回历史 |

初始化、增量迁移及已知授权写入在同一个 BEGIN IMMEDIATE 事务中更新相关状态；全局版本的原有语义不变。只读捕获发现旧 writer 留下的水位缺口时，将缺口纳入指纹而不修补数据库；下一次初始化或已知授权写入才折入持久 fallback_epoch。部分表缺失时在重建事务内更换文档 namespace，使丢失历史不能认证旧绑定。

## 5. 事务与并发边界

### 新稿捕获

AMInformation.evidence_bundle() 在原交互授权后选出唯一项目，再进入信息库事务获取一致材料和 v2 绑定。此前普通查询留在请求行上的全局版本不代表新文稿权限。

普通查询、跟进和通用会话仍保留原全局守卫。它们不能仅附带一个文稿字段就获得 v2 资格。

### 当前性复核

AMInformation.document_evidence_current() 依次执行：

1. 绑定版本、身份范围和期限校验。
2. 对 v1 执行原全局版本比较。
3. 使用既有 direct-return 身份路径检查本地拒绝和原身份租约。
4. 只读取最近一次完整本地项目快照，不触发远程刷新。
5. 在一个信息事务中按绑定原版本重建摘要。
6. 比较授权分项和完整状态，返回稳定的失败类型。

模型、平台读取和身份刷新不放在数据库锁内。生成前后、本地提交前及后续采用、保存、挂载、展示均保留原检查入口。

原暂停、取消、修订号和 120 秒任务期限保持。局部拼装仍用轻量检查，不在每个字符串处理步骤重复扫描信息库。

相关依据确实变化时仍拒绝旧稿。本修复不承诺在持续新增实质性材料时，旧稿可以不经重新核验直接发表。

## 6. 缓存、分页与发送

视图继续使用 am-document-view/1，绑定文稿、修订、范围、正文、分析、报告、规则、采用状态、目标和证据。公开 capture()/require() 接口保持兼容。

内部捕获同时返回本次已经核验的证据。只有实际进入标准文档验证、确有结果且证据为 v2 的草稿，才能取得专用标记。孤立结果或无结果的收集页不能取得标记。

### 6.1 两种来源记录分开保存

am_source_deliveries 继续保存原始 source_access_version，保持普通会话和 Harness 对来源版本的含义。

am_document_source_outputs 新增独立的 source_fence 字段，保存 am-document-source-fence/2: 标记。它不是权限授予，使用时须重新验证。

标记同时绑定实际 outbox 的以下不可变字段：

id、task_id、app、tenant、user、chat、chat_type、origin_chat_type、kind、body、artifact、nonce、created、expires。

因此不能把标记移给另一条消息、入队后更换正文，或延长有效期。

### 6.2 入队和发送前

notify() 先核验视图。v2 按相关证据检查；v1 和普通消息仍检查全局来源版本。v2 必须有可用的信息核验器。

valid_output() 对持久化标记要求：view 记录存在、当前仍是已验证的 v2、正文及期限摘要一致。缺记录、降级到 legacy/neutral、标记缺失或篡改均拒绝。

纯文本 document_result 也必须具有 view 记录，不能因为没有 card 或 query delivery 而遗漏检查。查询型输出还通过 query_delivery_authorized() 检查请求来源和当前查询范围。

原 Gateway 发送前检查和最终 transport guard 继续执行。一次检查内部可复用完全相同的 card/view 绑定；不同入队、发送和回调边界之间不能缓存“已通过”。

### 6.3 兼容与未决状态

v2 仅用于本轮专用文档视图、分页和完成通知。普通 conversation/harness 的来源守卫不放宽。专用输出不注册成普通会话回复来取得第二种身份。

旧未绑定缓存的清理保留。unknown/stop_unknown 等未决状态不因恢复服务自动重发。原文、视图或身份失效时只提供重新核验入口，不用旧缓存续期。

## 7. 正式挂载目标的字段和关系

### 7.1 显式区分文种与链接

配置必须显式提供 `project_code`、`project_type`、`document_type`、`document_kind_field` 和 `document_link_field`，并保留空间、项目、节点、交付物及其他字段绑定。`project_type` 是项目工作项实际返回的 `work_item_type.key`，不是文档模板里的 IRAD 等业务分类；交付物自身的工作项类型仍由 `type` 绑定。

`project_code` / `document_type` 是预期值，不能自证目标正确。适配器独立读取项目属性，从真实项目标题唯一解析业务编号；再依据 `document_kind_field` 的元数据、实际单值和可验证候选确认文种。本次没有按交付物名称猜测文种的兜底。URL 列表不能解释为文种。

`document_link_field` 指定实际追加和回读文档的写入字段。当前沿用附件上传与附件列表更新，只支持 metadata 类型为 `file` 的字段，**不支持 URL 列表写入**。字段名称或配置预期不能将 URL/link 字段变成附件字段。

| 字段角色 | 接受的 `field_type` | 当前支持的实际值形态 |
| --- | --- | --- |
| `document_kind_field`：文种 | `text` / `select` | 非空文本，或唯一候选的 value / `{value, label?}` 单值；不接受数组 |
| `document_link_field`：文档写入 | `file` | 现有附件对象列表或其 JSON 字符串；提交保留原附件并按 token、名称、类型、大小校验 |
| `project_field`：项目关系 | `work_item` | 单个 `{id: 项目工作项ID}` 对象，不接受多项目列表 |
| `node_field`：节点关系 | `text` / `select` | 文本节点 key 或已验证候选的 value，必须等于配置节点 |
| `approval_field` / `delivery_mode_field`：审核 / 交付方式 | `select` | 候选 value 或 `{value, label?}` 单值；提交时审核仍须为含 value 的对象，并等于 `unreviewed_value` |

`select` 元数据必须包含非空 `options: [{value, label}, ...]`，候选 value 不得重复；实际单值必须在候选中，响应携带 label 时还须与 metadata 一致。已审查的 `document_type_bindings` 可映射不透明候选 ID，但不能绕过候选存在性、实际读值或可识别文种标签冲突校验。其他类型、多选和未知候选格式返回具体诊断。

文种、写入、项目关系、节点关系、审核和交付方式这六个字段角色必须互异。旧 `document_field` / `attachment_field` 只作为兼容别名，必须分别与显式 `document_kind_field` / `document_link_field` 相同；**旧别名不能补全缺失的新配置**。只含旧字段或字段角色冲突的配置停止挂载。

上表是本适配器严格支持的响应契约，尚不构成原机真实 schema 已适配的证明。实际 metadata 形态不支持时，应保留阻断证据，先只读导出并审查，再做精确适配。

### 7.2 准确关系

目标需要形成可读回的链条：

业务项目编号 → 项目工作项 → 实际节点 → 节点成员交付物 → 文种身份 → 文档链接字段。

使用既有 Meegle CLI 的元数据和业务读取。项目与交付物分别核对 ID、所属空间和工作项类型；节点请求绑定配置项目，返回节点 key 必须一致，其原生下级工作项列表必须包含交付物。交付物上的项目关系与节点关系字段也必须明确返回并匹配，不能仅凭节点成员列表就忽略缺失或矛盾的关系字段。

字段未返回、分页不完整、成员不在节点、项目不一致、文种不确定、字段类型不支持或候选不唯一时，明确诊断并拒绝自动挂载。metadata 按页读取，最多 20 页；每页须返回 `list` 和布尔型 `pagination.has_more`，最终须明确结束。节点响应也必须有 `pagination.has_more: false`，不能把未知分页状态当成完整结果。

发现过程不选择替代项目或节点，不把配置 ID 的存在等同于关系有效。完整核验后唯一匹配为 `available`；多个匹配为 `ambiguous`，仍需明确选择。混合成功和未解决结果时返回 `unresolved`、清空 `targets`，已验证候选仅进入 `reviewable_candidates` 供审查。

### 7.3 身份与修订分开

target 增加 `document_identity`、明确的文种与写入字段、`field_metadata_fingerprint` 和 `binding_fingerprint`。不可变目标身份/字段元数据摘要与可变工作项修订、附件列表分别处理。写入前及上传后、字段更新前必须匹配原目标和完整 revision；写后对账比较不可变绑定，并核验唯一目标文件、既有附件 token 未丢失及实际下载内容哈希。正常追加造成的附件列表和 revision 改变不会被误判为另一个目标。

沿用采用、目标选择、挂载预览、确认、日志与对账。已有附件无法可靠保留时，在上传前停止；缺失附件字段仍不能自动当作空列表。保存附件不表示专业审核或节点完成。结果未知时先查原日志和回执，不重复挂载；旧 journal 缺少新绑定指纹时也不会被直接认定为成功。

### 7.4 同一次读取的期限与取消

可选 `read_scope` 使用每个 `MeeglePort` 的 `ContextVar`，把发现入口的同一个 `deadline` / `guard` 贯穿所有别名、metadata 页、`resolve` 和 `document_identity` 复读。嵌套作用域只能缩短期限，不能为下一页或另一个别名重开预算。普通 fake port 不需要实现此能力，原 `resolve` / `document_identity` API 不变。

`_run` 在每次 CLI 调用前后检查同一 guard 和剩余时间，subprocess timeout 为 `min(40秒, 剩余秒数)`。期限用尽或取消后不再发起下一次读取；`BUSINESS_READ_DEADLINE` 和取消码不包装成普通 metadata 错误。没有外层发现上下文时，单次 `_state` 也有 120 秒整体读取上限，并取当前 row `expires` 的更早期限。这项预算与原文档任务期限共同收紧读取，没有提高全局超时。

### 7.5 信息来源的拒绝、重试与配置迁移

以 `target_alias` 绑定 `document-business.json` 的 `project_snapshot` 来源由 `ExistingMeegleReader` 复用同一 `_state` 验证。准确项目编号/类型、节点成员、项目关系、文种或明确字段绑定校验失败，经精确错误码集合转换为 `PermissionDenied`。信息同步层将来源标记为 `denied`；从非 denied 转入 denied 时推进相应来源授权 epoch，并使在途旧租约失效。这样，错误目标不会继续作为可读的旧项目快照使用。

metadata 获取失败（`BUSINESS_METADATA_UNAVAILABLE`）、页数预算用尽（`BUSINESS_METADATA_LIMIT`）、整体读取到期（`BUSINESS_READ_DEADLINE`）、网络或未知临时异常仍走 `RetryableError`，不因错误名前缀就当作撤权。成功获取的 metadata 缺少必需字段或含矛盾定义，则属于前述明确字段绑定失败。此前已 denied 的来源不会被一次临时错误恢复。配置修正后须重新成功采集才能恢复可读；授权 epoch 不回退，旧 v2 绑定不会因恢复而重新生效。

因此，新增字段迁移也覆盖使用 `target_alias` 的既有 `project_snapshot` 来源：必须先审查并补齐这些别名的准确配置。独立完整 `MeegleProject` 项目采集路径不依赖这份挂载别名配置，不受此次新增字段要求影响。

真实 ID、字段、候选、节点成员和 metadata 形态由 Codex 在原机只读核对后配置。本包只证明合成响应下的验证与对账行为，不证明真实模型语义、原机 metadata 可读、实际挂载或独立业务验收已通过。

## 8. 行为矩阵

| 变化 | v2 文稿 | v1/普通查询 |
| --- | --- | --- |
| 心跳，内容、质量和权限不变 | 可继续 | 原规则 |
| 调度变化，有效新鲜度不变 | 可继续 | 原规则 |
| 默认新鲜度因 poll 改变 | 旧绑定失效 | 原规则 |
| 无关来源 ACL 变化 | 相关摘要不变可继续 | 原全局失效 |
| 相关来源撤权后恢复 | 旧绑定失效 | 原全局失效 |
| 当前项目台账或原文版本变化 | 旧绑定失效 | 原规则 |
| 新增未解析消息、相关缺口或任务集合变化 | 旧绑定失效 | 原规则 |
| 原文或身份租约过期 | 拒绝，缓存不续期 | 拒绝 |
| 正文、报告、目标、标记或 TTL 被改动 | 拒绝旧投递 | 原规则 |
| v2 绑定记录缺失或降级 | 拒绝 | 不能获得 v2 资格 |
| 目标关系或字段无法证明 | 不自动挂载 | 不放宽原挂载边界 |
