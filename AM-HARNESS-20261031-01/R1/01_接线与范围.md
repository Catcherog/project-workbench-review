# 接线与范围

原链路仍为 `bridge → AmSelfService → LegacyConversationBridge → ConversationAgent → ModelCoordinator → 原 Qwen`。没有增加飞书消费者、替换模型或改变授权来源。

## 入口与持久执行

`am_harness_host.py` 从原 inbox 读取身份与消息。明确控制先核对原 grant，再通过 IngressController 修改真实任务版本；控制有独立、有界 I/O 入口，普通 inbox 满时另保留有界控制容量。无任务的控制也记录幂等结果。

短读使用原 `request_context` 和 OneShotReadRunner；只有整体语法匹配且项目唯一的字段查询才命中。复杂请求经 TaskRuntime 持久提交；宿主单 worker 取得 lease 后，重新读取真实来源、当前权限和项目范围，再进入原 `_active` ContextVar。原模型协调器控制全部 Qwen 调用者。

初始请求、实际更正消息、`harness:run_id:vN` 内部事件分别保存。更正不会改写原消息正文。快查询只使用自己的短期焦点；长任务的原会话焦点由对应执行上下文更新。

## 发布与正式动作

DurableStore 使用原 gateway SQLite。发布回调只执行本地 SQL，使用调用方传入的 conn；原 `am_conversation_outputs`、`am_outbox_events`、grant、source-access 与群/thread 关联均保留。默认 `verify_legacy_binding` 执行严格来源检查，没有换成恒真 verifier。

原 Gateway 先完成权限核验，再在同一 pending→sending 事务内检查 fence。权限版本在实际 transport guard 处继续复核。入队后的取消会撤销尚未发送内容；已经进入 sending 或网络结果未知时保留原记录，不声称撤回。

原 ConversationStore 仍持有批准和执行占用。Harness 的动作 reservation 在原 gateway 库中与任务取消串行化，并在真实下游提交日志处再次检查：

| 提交位置 | 绑定内容 |
| --- | --- |
| `BusinessTools.send` | 当前 action、参数/预览 digest、确切目标、request key、原发送日志 |
| `Scheduler.approve_plan/revise` | 计划版本、hash、规则及原批准记录 |
| `ActionItems.change` | 确切事项、版本、动作与证据 |
| `NativePublisher.save` | 稿件 revision、accepted_hash、content_hash、指定字段与复制幂等键 |
| `LogicService.mount` | 稿件 revision、采用指纹、准确目标、挂载幂等键 |

会话动作库与业务库并未被称为一个跨库原子事务。原动作占用是执行权威，新增 reservation 记录的是提交准入和结果；中断及回执丢失继续按原未知结果机制核对，不自动重放。

## 来源、历史、缓存与观测

并行补修的 `source_access_version` 已进入实际 context。旧派生助手历史使用原 `_derived_fingerprint` 过滤，用户原话保留原权限指纹；Harness 还会过滤取消、失败、旧 revision 和未核实派送的助手回复。checkpoint 的权限指纹也包含来源访问版本。

当前来源投影保存 source_id、project、version、观察时间、有效期和 reported 状态，保留原内容中的计划、预计、待核和确认条件。历史只按完整消息选择，过期或权限变化不续期。checkpoint 仅复用纯来源投影，正式批准和外部动作不从缓存重放。

工具仍调用原 registry 的 schema、角色与项目检查。独立工具并行白名单为空；新短读入口的并发不等于全部业务工具可并行。

元数据 trace 只记录常量标签、哈希任务引用、计数和时长；不记录 prompt、回复正文或准确用户 ID。first_useful/final 以原消息真实回读为准。原后端 token 用量与完整提示 UTF-8 字节同时记录，字节预算未标记为精确 token 估算。

快读回复同样记录实际项目和快照版本；重复事件不会更新其原始来源版本或期限。来源内容/权限变化会过滤派生回复，用户原话则继续按原访问指纹与原始期限处理。执行失败或隔离状态有不含业务数据的独立提示，仍走原身份与发送通道。
