# 验证证据与真实环境验收

## 1. 本地证据如何读取

本轮最终固定源码验证结果：新增测试 **130 项通过**；补丁后原 AM 会话回归 **138 项通过**；合计 **268 项，0 失败、0 错误、0 跳过**。固定来源 270 个文件（当前源 184 + 历史测试参考 86）逐个 SHA-256 核验通过，engine patch 检查和语法检查通过，验证期间源码保持稳定。Python 3.12.14。

`evidence/summary.json` 是最终机器可读结论。它记录 baseline hash、补丁检查、测试回报、Python 版本和源码在测试期间是否稳定。`evidence/harness/` 是新增模块/集成测试；`evidence/am-regression/` 是补丁后原 AM 会话回归；各有完整日志和 JUnit XML。

本地验证实际运行 SQLite、线程竞争、多进程抢占、文件持久化和原 AM 类。模型、飞书端点与项目事实使用合成 fixture。没有由这些测试推导“真实自然语言成功率”或“线上快多少”。原 fs_agent pytest 全套尚未在本轮执行，需 Codex 原环境补跑。

重点覆盖：

- 多线程重复 submit 只产生一个任务；多进程只有一个 claimant。
- 同 actor 不同 chat/thread、不同 actor/app/tenant 的范围隔离。
- 模型阻塞时取消/更正立即入库，旧结果不调用后续工具、不发布。
- 取消不提前释放模型 lane；lease 超时与进程重启仍隔离。
- 同 revision 重排后的旧 generation 无法继续执行或派送。
- pending 回复可同事务撤销；sending 后保留 unknown/真实 receipt。
- 事务失败回滚，提交过程中越过期限也不能发布。
- 原来源链、事件 hash、真实更正消息、群 thread/引用和 payload 完整性。
- 上下文及 checkpoint 的权限、来源版本、撤销和 TTL 失效。
- 原 history 已提交但派送前取消时，失效 revision 不再进入后续模型历史；未核实投递的助手回复不伪装为用户已经看到。
- 工具异常、并行批次后撤权、超时 may_continue、外部 handler 不被通用批执行器调用。
- 原 AM bridge 安装快路后模型调用为 0、outbox 幂等，恢复 callback 后回到原 provider。

## 2. 合成演示

```bash
PYTHONPATH=src python3 -m am_harness demo
```

演示会暂停一个合成 worker，提交更正，确认旧 lane 仍被持有，释放旧 worker 后运行新 revision，再取消尚未发送的输出。通过条件为旧结果 stale、新版本完成、只有一条有效 outbox、取消后其状态 rejected。临时库自动清理；没有网络调用。

演示为简化 fixture 显式传入 synthetic binding verifier。生产代码必须使用 `FencedOutbox(tasks)` 默认的真实 AM verifier，不能复制 demo 的测试替身。

## 3. 真实环境最小验收矩阵

机器可读清单在 `evaluations/live-cases.json`。至少按以下范围完成同一最终 commit 的回归：

| 组 | 场景 | 必须观察的证据 |
|---|---|---|
| 明确查询 | 四字段、别名唯一、有效焦点追问 | 内容与原来源一致；模型调用为 0；来源时间和缺失限定正确 |
| 保守回退 | 同名项目、多项目、综合分析、修改/发送混合 | 不误走快路；不漏掉后半句要求 |
| 原功能 | 项目查询、跟进笔记、原卡片命令、文档准备 | 行为无退化；原回读和权限仍生效 |
| 控制 | 排队取消、模型中取消、模型中更正、重复控制 | 入口不等长任务；旧结果不投递；新 revision 只执行一次 |
| 崩溃恢复 | worker 中断、lease 到期、进程重启 | 隔离持久；无第二个重叠模型；无 unknown 自动重发 |
| 发送竞争 | pending 后取消、sending 后取消、回执丢失 | 前者撤销；后者待核对；不得谎称撤回或重复发送 |
| 身份 | 私聊、群聊、引用、thread、真实同事、撤权 | 各读取和派送均在当前范围；无串会话/串线程 |
| 上下文 | 长历史、来源变更、TTL 到期、缺资料 | 不延长 TTL、不把 reported 升为 confirmed、不截断关键指令 |

正式发送场景仅在已有授权的测试对象与范围中执行。用户未授权的对外消息不属于代码包交付本身；按原项目已有测试授权开展，不扩展对象。

## 4. 建议的门槛（待实测，不是已经达到的指标）

**硬性正确性门槛**：新增越权读取/投递为 0；重复外部效果为 0；旧 revision 发布为 0；过期来源进入上下文为 0；原批准与 accepted_hash 检查不退化。任一出现则不能凭时延改善判通过。

**交互指标**：控制请求从原入口接收至任务状态提交单独记录，建议 P95 ≤ 1 秒；这不等于模型/GPU 停止时间。来源已经就绪、唯一明确字段查询建议服务端有效回复 P95 ≤ 3 秒；冷源刷新单独分桶。用户可见时间必须由实际飞书投递/读取边界获得，不用 callback 返回时间替代。

**整体比较**：同模型版本/量化、相同机器、同来源快照和冷热缓存条件下，baseline 与 candidate 使用同 case/trial 配对，记录首个有用回复和最终完成的 P50/P95、模型调用次数、输入输出 token、取消丢弃数和业务结果。建议每个关键分桶至少 20 对完整样本；汇总样本不能掩盖关键场景退化。

`evaluation.analyze` 的 minimum_pairs 是输入比较的最低数量，不是统计显著性证明。正式性能报告应同时给出样本数、分桶、误差/波动以及正确率；暂不承诺固定提速倍数。

## 5. 证据格式

每行 JSON 至少包含 case_id、trial_id、environment_id、arm、live_model、live_transport、success、first_useful_ms、final_ms、model_calls、unauthorized_reads、duplicate_effects、stale_publications。`success=null` 表示尚未完成正确性审核，不算通过。

```bash
PYTHONPATH=src python3 -m am_harness evaluate /absolute/path/to/normalized-evidence.jsonl
```

排除 synthetic 或缺真实传输的记录；只有环境相同的 baseline/candidate 才形成配对。环境指纹的计算与实际打点需 Codex 在原部署补齐，不能伪设 live flags。真实用户反馈、手机端使用与工程文档业务验收单独记录，不能由单元测试代替。
