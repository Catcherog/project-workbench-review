# 原 AM 接入、迁移与回滚

## 1. 先确认当前树，不覆盖旧快照

本包基于 review commit `7445333757fd39b674caa7cca8237ee9ecc46f89` 的 `AM-CONVERSATION-20261030-01/R1/`。该快照的 source commit 是 `d0bb75cfe372190b166b684afffd974a6f2f60d5`，并包含并行信息层、文档与 UX 依赖。包内 `baseline/manifest.json` 保留原文件清单，`scripts/assemble.py` 对实际交付的 184 个非旧 overlay 文件核验 hash。

Codex 应先读取 Studio 当前 AM worktree、已有变更、当前交接和实际配置。若最新树与固定基线不同，以当前用户确认行为为主，逐函数合并 patch；不要用本包 baseline 覆盖工作树，也不要用旧配置覆盖后续已授权的 Qwen、飞书和资料接入配置。

## 2. Phase 1：原引擎内部快查询

这一步有完整可执行代码，也已在真实 `LegacyConversationBridge` 类上做本地集成测试。

1. 将 `src/am_harness/` 加入原 AM 的 Python 模块路径，或离线安装本包。
2. 在原会话代码中合并 `integration/engine.patch`。未传入 lifecycle/fastpath 时保持原行为。
3. 在原 `LegacyConversationBridge` 创建完成后、业务 worker 启动前安装：

```python
from am_harness.install import install_fastpath_only

fastpath_installation = install_fastpath_only(am_service.conversation)
```

需要回滚该功能时：

```python
fastpath_installation.restore()
```

安装器只改 `agent.fastpath`，不会创建模型、发送器或消费进程。恢复会检查 agent 和 callback 仍由本次安装拥有，防止覆盖并行变更。已有 lifecycle 的 bridge 不能使用分步安装器。

这一步减少明确查询的模型调用，但请求仍受原 `am_query.pump` 的同用户 I/O 排队与引擎会话锁约束。**模型忙时也能立即读**需要下一步独立只读路径，不能用 Phase 1 的测试结论替代。

## 3. Phase 2：入口三分流与持久 worker

原代码的关键位置：

| 文件/函数 | 当前职责 | 需要的接线 |
|---|---|---|
| `local-qwen3.8/feishu-bridge/am_service.py` 的 `AmSelfService.ingest` | 鉴权后的原消息进入 inbox、自然语言路由 | 原身份/范围校验后优先识别明确控制，不能排在同用户正在运行的 future 后面 |
| `am_query.py` 的 `QueryMixin.pump` | ThreadPoolExecutor、同用户队列、conversation future 上限 | 为短读和持久 turn 分开准入；保留唯一原消费者与有界 I/O 并发 |
| `am_conversation/legacy.py` 的 `LegacyConversationBridge.process` | 构造 ctx、建立 `_active`、引擎调用、render、原 outbox 事务 | 拆出可信请求上下文、引擎执行与提交三个阶段，避免重复消费和重复发送 |
| `am_conversation/engine.py` | 原会话循环和业务动作 | 使用已给 overlay，接 LifecycleBinding |
| 原 Gateway 的 pending → sending 事务 | 最终派送准入 | 在同事务内增加 FencedOutbox.before_dispatch，并保留原全部检查 |

### 3.1 启用后的对象关系

以下在 Phase 1 已安装 router 的基础上展示已有模块的真实 API 组合。`authorize_scope`、`resolve_current_context`、`publish_original_outbox` 是 Codex 必须在原宿主实现的三个适配合同，不是本包内已有函数；它们依赖 Studio 最新的服务实例和库路径，不能用恒 True 或空函数代替。

```python
from am_harness.am_adapter import LifecycleBinding, AmAgentRunner, OneShotReadRunner
from am_harness.config import HarnessConfig
from am_harness.controls import IngressController
from am_harness.effects import FencedOutbox
from am_harness.runtime import TaskRuntime
from am_harness.store import DurableStore

config = HarnessConfig(enabled=True, fastpath_enabled=True,
                       control_enabled=True, durable_queue_enabled=True)
tasks = DurableStore(original_am_database_path, max_queued=config.max_queued,
                     aging_seconds=config.aging_seconds, clock=am_service.s.clock)
effects = FencedOutbox(tasks)  # 默认启用真实 AM 来源链验证
hooks = LifecycleBinding(tasks.guard, clock=am_service.s.clock)
am_service.conversation.agent.lifecycle = hooks

runner = AmAgentRunner(am_service.conversation.agent, resolve_current_context,
                       hooks, clock=am_service.s.clock)
reads = OneShotReadRunner(am_service.conversation.agent, hooks,
                         clock=am_service.s.clock)
runtime = TaskRuntime(tasks, runner, authorize=authorize_scope,
                      publish=publish_original_outbox, config=config)
controls = IngressController(tasks, authorize=authorize_scope,
                             on_change=effects.suppress_pending)
```

生产 callbacks 的合同如下。

**authorize_scope(scope, operation)**：scope 仅来自原入口鉴权；submit、control、execute、publish 都要核对当前功能开关和当前身份/项目权限。read 身份缓存仍使用既有固定飞书 ID 和 600 秒机制；管理/执行仍调用原强校验。不能把存储的 allowed projects 当永久授权。

**resolve_current_context(snapshot)**：读取真实原 inbox 来源行，重新核对 grant、可见项目、群引用和 thread；建立原 `bridge._active`，yield 原 `AccessContext`，finally reset。内容 TTL 取 run 与来源更早的值。不要把 ContextVar 作为普通全局变量；并行请求必须隔离。纠正后的真实来源事件从 `am_harness_events` 的当前 revision 查询。

**publish_original_outbox(conn, run, result)**：在执行已结束且授权已复核后，通过传入的**同一 SQLite conn**调用原 notify 的本地插入；保存原 `am_conversation_outputs`、`am_outbox_events`、`am_query_deliveries` 等关联，再调用 effects.bind/enqueue。调用时不要重新打开 `self.s.tx()`，不要在这个短事务里重新请求远端权限、刷新来源或发送网络消息。

需要用于 render 的 grant/context/source metadata 应在提交前准备成明确数据，再在事务中核对 fence 和本地版本。原字段格式、`_plain_text`、`display`、project_refs、preview verification 的行为必须保留。

### 3.2 三条入口

- 明确控制：持久保留真实控制消息后，调用 `controls.handle`。命中后发送固定数据量的控制回执，原事件不得再进入模型。无任务/歧义的 no-op 也已经幂等落库。
- 明确短读：在新鲜原请求上下文内调用 `reads.try_handle(ctx, incoming_event_id, text)`。返回 None 才提交复杂队列；返回有效回复走原 reply/render/outbox；返回 in_progress 则等待原事件的既有处理，不能再提交模型。
- 复杂任务：调用 `runtime.submit(...)`，由原业务循环管理唯一 worker 调用 `runtime.run_once(worker_id)`。没有待处理任务时返回 idle。不要再让原 conversation future 同时处理相同 inbox 行。

引擎安装 strict lifecycle 后，所有普通 `handle()` 必须经持久 fence 绑定。漏接线报 `HARNESS_UNBOUND_RUN` 应修复调用链，不能把 strict_bound 改为 False 掩盖问题。

## 4. 三类事件 ID 必须区分

| 名称 | 示例/来源 | 用途 |
|---|---|---|
| 原始请求 event ID | `run.event_id`，真实 inbox ID | 原始任务追溯、submit 幂等 |
| 当前要求来源 event ID | v1 为原事件；v2+ 为真实 revise 控制事件 | `am_conversation_outputs.event_id`、原 outbox 来源关联、原输入 hash |
| 引擎内部 event ID | `harness:<run_id>:v<revision>` | 原 ConversationStore 的版本隔离、reply.event_id |

派送幂等键使用 `deterministic_publication_key(run)`，含 run ID、revision、cancel epoch。不能继续用初始 `conversation:<original_event_id>` 发布纠正后的回复，否则会命中已经撤销的旧 outbox。也不能为通过校验伪造 inbox 事件，或者修改原用户消息正文。

`legacy_binding.verify_legacy_binding` 已实现上述检查，包括原 submit hash、真实 revise 指令与 replacement、五元身份、thread、群引用、grant hash、原输入 hash、TTL 与 engine event。它会拒绝尚未完成宿主接线的记录；这属于明确集成失败，不是应当放宽的规则。

## 5. 外部动作与待批准草稿

新任务控制和原业务确认继续分离。原 `_control`、action digest、版本、presented_version、verified preview、accepted_hash 均保留。原 in-flight/unknown 动作仍需要单独对账。任务控制不能生成 approved action。

Codex 需逐个检查 `BusinessTools`、文档提交、提醒/发送执行器：将当前 fence 带到真实动作 reservation；参数、版本和接受 hash 必须一致。跨数据库不能只靠两个顺序事务声称原子，应复用原动作记录作唯一执行权威，必要时加入同库 reservation 记录和可恢复的对账流程。本包不提供“重放全部工具调用”的恢复开关。

在这部分接线通过前，完整 harness 先限于读任务/明确无外部效果的任务；原业务功能可继续走原既有流程，不把未绑定的确认请求送入新的可取消执行通路。

## 6. Context / checkpoint / 并行读接入

这三个组件已实现和测试，但未替换原 `_run` 的上下文格式，也未批量改写现有工具。

完整 worker 启用时先接上已交付的历史过滤 facade，避免旧 revision 在取消后遗留到模型历史。保留原 store 作为唯一写权威，只替换 history 读取：

```python
from am_harness.history_adapter import FencedHistoryStore

history_store = FencedHistoryStore(am_service.conversation.store, tasks)
am_service.conversation.store = history_store
am_service.conversation.agent.store = history_store
```

该适配器使用固定基线的 `conversation_messages` 与 `_access_fingerprint` 契约，Codex 需核对最新 schema；原工具闭包仍持有原 store 可以继续使用。harness 助手历史只有在真实 sender 的 verified receipt 镜像写入后才可见。

- 从原信息层为每条 fact 提供 source_id/version/observed_at/expires_at/project/evidence_state，未知来源状态保持 unknown/reported。将任务笔记与正式事实分开。
- 原消息历史没有可证明来源 TTL 的摘要，不宜硬拼成长期 MessageBlock；先保守保留原会话策略，再增量补充来源映射。
- 将 checkpoint 接到明确可复用的阶段，例如读取结构化事实、模板来源解析、纯内容检查；输入、依赖版本、权限任一变化即失效。
- `AmRegistryAdapter` 可直接适配原 registry。只有经线程安全与访问范围复核的 read 工具加入 `independent_read_tools`；默认空集合。不要并行执行修改工作笔记、批准、发送或写台账。

## 7. 数据库、运维与回滚

任务库采用独立连接、WAL、busy_timeout 和短 `BEGIN IMMEDIATE`。默认不接受内存库。共库接入前备份原数据库并确认原连接策略；如果实际原 SQLite 位于不支持可靠锁的共享文件系统，应先解决部署存储，不能用关闭锁绕过。

定期调用 `purge_expired()`，并按原维护策略处理 WAL/备份保留。这里的 TTL 是逻辑过期，不承诺磁盘取证级安全擦除。状态 CLI 只读元数据，不显示正文、不创建 schema、不清 pause：

```bash
PYTHONPATH=src python3 -m am_harness status --database /absolute/path/to/am.sqlite3
```

回滚先停止新的 harness 准入，保留正在发送和 unknown 的原动作状态，等已知 worker 返回或完成对账，再恢复旧路由。不得删除任务库或旧 outbox 以“清故障”，否则会丢掉重复事件墓碑与未确认效果。Phase 1 仅用安装器 restore 即可恢复此前 callback。
