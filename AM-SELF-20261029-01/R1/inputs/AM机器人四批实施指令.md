## 3. 共用数据与状态约定

### 3.1 在 AM 内持久化

优先扩展现有 AM Store。当前 tasks 是推理任务表，不能直接兼作长期业务事项。

新增或等效实现以下对象：

| 对象 | 必要信息 |
| --- | --- |
| ProjectRef | AM 稳定 ID、来源 namespace、已核实业务编号、名称/别名、当前定位、身份状态 |
| SourceRecord / Fact | 来源身份、版本/内容指纹、原文定位、对象、属性、值、条件、时间性质、证据状态 |
| ConversationState | tenant/app/chat/user/thread、引用关系、焦点、原问题、待澄清候选、有效期 |
| ProjectSnapshot / ChangeEvent | 前后快照、字段旧新值、完整性、读取时间、稳定变化事件 ID |
| ActionItem / Feedback | 事项、项目、责任人、交付要求、日期、业务状态、反馈、核验者、关闭依据 |
| ApprovalSnapshot | 动作、发送/写入身份、准确目标、完整内容、业务版本、hash、批准人、时效 |
| ReminderPlan / Occurrence | 计划版本、北京时间规则、目标、批准策略、单次实例、执行窗口、状态 |

ProjectRef 的最小身份支持是 A/B 的共用基础，可在 A 先建立，B 再完成映射管理和快照。新字段采用迁移编号及必要索引/唯一约束，不通过清空库解决兼容问题。若 GroupLedger 仍使用独立 SQLite，明确跨库只有事件关联，不能宣称一个事务覆盖两个独立连接。提醒预览与自身 outbox 的原子建立必须在同一 Store 事务中完成。

### 3.2 所有外部动作的共同语义

- 稳定 request/action ID；输入重放不创建新的业务动作。
- 批准使用服务端保存的独立不可变快照，不能依赖卡片数组位置。
- 发送/写入意图先落库，外部调用后保存回执与核验状态。
- confirmed_not_sent、sending、unknown、sent、readback_verified 分别表达；不要把“没有 message_id”认定为未发送。
- 明确未发送且可恢复的失败可在原授权、原目标、原正文和原时效内有限退避重试；遵守 retry-after，默认总尝试不超过 3 次。
- unknown 只进入受控对账队列。对账重试与重新发送是不同动作；到达次数/时间界限后形成待核对项。
- 同一动作的重试继续使用原幂等身份；平台 UUID 的短期防重不能替代本地账本。
- 取消阻止未开始的动作。调用已开始时只记录取消请求并核实结果，不谎报撤回、回滚或未发送。
- UI 超时、模型终止、平台发送结果是不同状态；不得互相代替。

### 3.3 时间与保留期

- 内部使用规范时间和时区，统一按 Asia/Shanghai 解释用户相对时间；解析锚点是原消息发生时间。
- deadline、预计日期、检查时间、发送时间分开。例如“明天 17 点前交报告”不自动等于“明天 17 点发消息”。
- 现有聊天原文继续绝对 24 小时清理；活跃业务事项、计划和对账必要记录使用独立生命周期。
- 不通过无限延长聊天 TTL 保存业务状态；只保留纳入事项的必要事实与最小证据。
- 提供业务记录保留配置、清理预览和幂等墓碑。活跃/unknown 不被聊天清理误删；若依据必须清理而对账未解决，应停止执行并保留结果未核实状态，不因证据消失恢复可发送。
- 技术方案提出终结记录的最小合理保留期并在交接列明；未经既有策略或明确启用决定，不擅自扩大原始私聊/群聊保存范围。

并发反例用事件屏障/假时钟稳定构造，避免 sleep 碰概率。原 reproduce_issues.py 的成功退出意味着“复现缺陷”，修复后要转成断言正确行为的回归，不能把退出 0 当修复通过。

## 5. B 批：入口、真实快查、来源快照与本人简报

### B1. 本人私聊独立完成日常提醒

沿用 EmbeddedPoC → Gateway → ReminderService → 原 bot 发送。

- 菜单和自然语言能创建、选群/人员、修改、预览、确认、取消、查状态和对账。
- 一次完整预览显示准确 bot、群、人员、正文、明确日期和发送方式。
- 同名候选由程序核验 ID；模型姓名/ID 不能成为授权。
- 帮助按真实 enabled/ready 状态显示能力；合成 sample 明确标记并退出日常主入口。
- 本人能独立走完流程，不需 Codex 手动拼目标/正文。
- B 仍是确认后立即发送；未来发送由 C 的计划承接。

### B2. 稳定 ProjectRef 与真实私聊查询

当前是 Sheets，parse_rows 以规范化标题为 key、行号为定位；不能假定有 Bitable record_id。

建议 ProjectRef：

- 当前定位；

业务编号优先映射；改名和排序不更换身份。缺号、重复号、编号变更不能靠模型相似度合并；由本人确认具体映射。B 不给远端加 ID 列，不改台账结构。

新增本人私聊的真实项目查询，与群共用取数和渲染。不能用假群绕过 group guard；需独立的私聊鉴权。当前 /progress sample 的合成执行标记不可直接套在真实远端查询上，迁移时明确 execution_kind。

### B3. 本人待办与可解释异常

支持：

- “今天我需要跟进什么”；
- “这个项目现在卡在哪”；
- “哪些项目的责任人、日期或资料还待确认”。

TH2“待办”按既有规则表示项目负责人需要推动的动作，可作为本人项目跟进清单来源；若原内容只是工程师岗位职责或归属不清，不擅自当作本人亲自执行任务，标注责任待确认。

没有明确今天时间的重点另列，不编造截止。预计、承诺、正式要求、检查安排分别表达。未更新不等于停滞，正常等待不等于异常；部分完成不变成全部完成。

### B4. 快照与变化事件

新增 project_snapshot、change_event 或等效对象：

- 保存最小必要字段、来源定位、版本/内容指纹、业务事实时间、来源更新时间、本次读取时间与完整性。
- 首次完整读取建立基线，说明无可比较历史。
- 程序比较确定字段；同内容重复读取不产生事件。仅文本变化只能确定“记录文字变化”时，不擅自升级为完成、批准或承诺变化。
- 同一变化事件有稳定 ID；改排序不产生业务变化，改名不生成新项目。
- 读取失败、表头变化、不完整、权限失败不推进成功基线；不能把缺行认定为删除或取消事项。
- “查询变化”不消耗推送游标；本人反复查询可以看到同一历史变化。
- 推送按 subscription＋event 去重；只在确认发送结果后推进已投递记录，unknown 保留原动作。
- 现有读取范围若不足以覆盖源表，明确 partial，不能把截断的列表当完整。

简报优先包括：新增变化、待跟进、日期变化、阻塞/缺项、需本人决定，逐项带原值/新值/来源/时间。模型只整理说明。

### B5. 简报订阅接 C 的调度

B 先完成主动查询与订阅模型；自动投递在 C 完成后联验，不阻塞进入 C。没有用户实际订阅不默认创建每日推送。主动订阅后使用 C 的同一调度器，不另起独立 cron。

可支持每天或工作日固定时间发本人；预览时间、范围和停用方式。群简报按第三方外发批准规则处理，不能从本人订阅扩大到群。

## 6. C 批：AM 自身的长期事项、反馈与持久调度

### C1. 创建独立业务事项

ActionItem 至少包含项目、稳定事项 ID、版本、发起者、责任人、核验者、描述、交付要求、来源、截止性质与时区、状态、最近反馈、下次跟进、关闭人及依据。

状态：待反馈、处理中、受阻、已提交待核验、已关闭；另有取消。暂停作为执行控制保留原业务进度。

- 本人明确发起或确认纳入才建立长期事项；不把 B 扫描到的所有待办自动建单。
- 支持查询、改检查时间、暂停、恢复、取消和关闭；这些修改仅作用于 AM 事项，不隐式修改正式项目日期/优先级/责任人。
- 不增加自动 P0、自动改正式项目优先级或自动转派。
- AM 本地关闭只结束本地跟进；正式项目、节点或交付物状态仍取原业务系统。
- 负责人“收到”只记录响应，“已提交”进入待核验；明确核验者或已配置且有实际证据的规则才能关闭。
- 默认由事项创建的 owner 核验；需其他专业核验者时必须有明确人员映射，不能根据职位名称猜授权。
- 所有改变带 expected version 和幂等操作 ID。迟到反馈保留为证据，不覆盖之后的人工决定。

### C2. 反馈卡与原消息关联

提供“已收到／预计完成时间／需要协助／已提交材料／非本人负责”。

服务端核验 app、tenant、实际操作者、事项 ID/版本、来源卡片/消息、nonce 与操作权限。可操作人限责任人或明确代办人；群内可见不等于有权更新。

- 反馈绑定卡片原事项，不依赖当前聊天焦点。
- 重复点击只产生一次有效反馈。
- 非本人负责形成待调整，不能自动转派。
- 接收材料保留来源与提交者，不能据此认定成果审核通过。
- 原提醒、反馈、事项、后续消息建立稳定关联。
- 支持本人查看跟进历史与剩余动作，区分消息发出、反馈、提交和核验结果。

### C3. 计划与实例分开

ReminderPlan 至少包含事项、计划版本、时区、触发/周期、下一时点、静默规则、日历版本、群/人员、模板版本、批准策略、起止有效期、停止条件和启停状态。

ReminderOccurrence 至少包含计划/版本/计划时刻、事项版本、批准快照、完整 payload/hash、稳定请求键、执行窗口、尝试次数、平台消息 ID 和回读状态。

唯一约束至少为 (plan_id, plan_version, scheduled_at)。同一实例重试不换 ID 或新建另一个实例。

### C4. 三种批准模式

| 模式 | 必须明确的批准范围 |
| --- | --- |
| 立即一次 | 准确目标、正文、当前版本及立即窗口 |
| 指定时间一次 | 上述信息＋北京时间发送时点和执行窗口 |
| 周期规则 | 事项、群、人员、模板和允许变量、频率、有效期、停止条件、错过时段策略 |

第三方周期发送默认到期生成待本人确认的预览。只有用户明确批准整个固定规则，才可在批准范围内生成自动执行实例。

规则批准不能允许模型临场生成任意正文。动态字段必须来自允许的结构化来源，正文含义、收件人、频率或期限变化都升级计划并使旧批准失效。每次实例保留其实际渲染正文和批准依据。

一次提醒的批准不能顺延为明天执行，也不能变成周期授权。计划的“长期有效”不代表某个过期实例仍可发送。

### C5. 调度与工作日历

- AM 内仅一套调度服务，复用 SQLite 事务和现有进程运行体系，不增加第二个飞书消费者。
- 可以用短周期扫描生成到期实例；扫描周期可按当前运行能力选择。不要用阻塞 sleep 承担长期计划。
- 工作日历需来源、版本、核实时间、覆盖范围及实际工作日；不根据周一至周五假设调休日。
- 普通提醒沿用已确认的北京时间 09:00/14:00时段及18:00后、休息日延到下一工作日09:00规则；具体计划仍明确频率，不为每个事项自动同时设置两个时段。
- 主动查询/取消不受免打扰影响。用户准确批准的特殊时间按其明确策略执行，不能暗改时刻。
- 日历不足时只暂停依赖它的计划，提供待核实状态；明确独立于工作日历的一次性时刻可继续按批准规则处理。
- 计划预览必须显示实际触发规则和执行窗口。默认不授权过期补发；修改窗口也属于计划版本变化。
- 进程停机跨多个时段后，重新判断当前需要，跳过已失效实例；符合当前有效窗口的最多一个实例可执行，不集中补发历史时点。
- 关闭/取消/暂停后停止新实例，发送前再次核对当前状态、版本、权限、批准和期限。
- 领取超时不能直接将 sending 重置为 pending；可能已调用平台的实例先 unknown/对账。
- 存在未核对的同一事项同一催办结果时，不再生成可发送重复通知；独立事项继续处理。

### C6. 重试、对账和清理

- 明确未发送的可恢复错误：受限退避、同实例同请求键、原批准仍有效。
- 超时/断线/崩溃：unknown，先核对；没有消息 ID 仍不能假设未发送。
- 回执迟到只归属原实例，不反向覆盖新计划或人工决定。
- 事项和计划不依赖原聊天未过期；业务 source 最小证据与引用独立保存。
- cleanup 不删除尚在处理的业务身份、批准摘要或 unknown 的必要信息；过期执行权不能复活。
- 暂停、恢复、取消和业务关闭都可在本人私聊完成，状态可见，不需要访问工作台。

## 7. D 批：受审进展采集、台账局部写回和附件预检

### D1. 显式进展采集

仅接受明确更新触发，例如：

“@AM 更新需求75：上电测试今天完成，报告明天下午提交，低温复测还没做。”

分开记录三种事实：上电测试自报完成、报告预计交付、低温复测未完成。不得合并为全部测试完成。

持久采集对象包含原消息/群/话题、报告人、发生/接收时间、原文指纹、ProjectRef、分条事实及原文位置、日期性质、核对版本、提案/写回状态。

流程：

1. 核验报告人和项目范围。
2. 留存原消息与最小必要证据。
3. 报告人核对系统解释。
4. 形成准确台账差异。
5. owner 批准当前差异范围。
6. 最小单元格写入。
7. 独立读回。

报告人核对不等于专业验收或写入授权。报告人与 owner 相同时，可在一张完整差异卡明确合并核对和写入批准，避免重复确认。

更正须引用原事实；原消息撤回/更正使未执行批准失效。已写回的内容形成更正候选，不能自动恢复整行旧快照。平台不能实时提供撤回事件时，记录检测范围，并在写前检查当前可读状态。

### D2. 写入对象和批准字段

当前 TH2 是 Sheets：

- 元数据读取使用 sheets/v3 ... /sheets/query；
- 值读取使用 sheets/v2 ... /values；
- 表头按名称解析，项目进展可有已核实别名“项目信息”。

新增 LedgerWritePort 或等效适配；MeeglePort 是交付物挂载，不是台账写入器。

首版允许列表只包含已授权台账、已批准项目的“待办”和“项目进展／项目信息”单元格。关键日期、人员职责、两类优先级、标题、表结构及其他字段不隐式修改。

LedgerChangeProposal 包含精确源、ProjectRef、提案版本、每个字段 before/after/before_hash、来源/保留/新增/更正说明、读取时间/版本、报告人核对版本、批准人/hash/期限、稳定请求键。

卡片展示项目、字段、修改前后全文、来源及自报/待核实性质。支持只批准一部分字段；实际写请求只能包含被批准子集，保存其准确批准快照。

### D3. 沿用 TH2 台账规范

以下为 th2-ledger-maintenance v1.0.0 的本轮相关规则，属于写回格式约束：

- 待办是需要项目负责人推动的协调、催办、确认、决策、组织验收等动作，一条一行。通常1至3项，但不能为凑条数删掉有效动作。无当前待办写“—”，不代表项目完成。
- 项目进展首行只放一个摘要核对日期，随后按“进度：／问题：／下一步：／要求：”顺序分类，每条一行。没有实质内容的标签可省略，未知不能写无问题。
- 同一事项在原位置更新，未被新消息提及但仍有效的成果、风险、前提、要求和验收条件继续保留。
- 完整排期、长期分工保留在原相应列，不能删除唯一事实；本批不因引用到日期/人员就修改其他列。
- 新计划不覆盖原批准基准，部分完成不变全部完成，申请不变批准，供应商报告不变本项目验证通过。
- 只保留一份当前摘要，不堆积每日历史段，也不把旧摘要搬进备注。
- 该台账显示日期遵循2026-10-28规则：YYYY.M.D，不补零。内部规范时间继续使用明确时区。
- 首行核对日不表示所有事实当天发生或重新验证；仅格式修改保留原摘要日期。
- 月初10日、中旬15日、月底/月末、年底12月31日的既有映射，只用于年月明确的计划显示，并保留原语义/精度。不得把显示换算值自动用作C批精确承诺或发送时刻。
- 人员用已核实AR编号＋姓名，保留真实链接/提及；不能猜编号，也不能因格式整理触发通知。

### D4. 最小写入、并发和未知结果

写前：

1. 按稳定项目身份重新定位唯一行；不沿用旧行号。
2. 重读表头、目标字段及必要的原值、公式、样式、备注、富文本链接/提及、校验等状态。
3. 核验 owner、准确批准范围、提案版本、来源依据和有效期。
4. 比较批准的 before 与当前相关字段；有冲突则重建差异，不原样重试旧内容。
5. 本地事务保存写意图与幂等键，再调用平台。

写中/写后：

- 只修改获批单元格；不整行/整表覆盖，不触碰相邻格式或业务字段。
- 执行前核实当前官方接口的条件写入/原子更新能力。读到 revision 不能自动当作 CAS 参数。
- AM 的目标锁只能约束自身并发，不能锁住人工或其他客户端。无服务端条件更新时，使用当前值复查、最小写入、目标互斥与前后核对，并如实记录剩余竞争窗口。
- 不把缺CAS作为停止全部D开发的理由；受控目标可以完成链路验证。若正式目标存在无法隔离的并行编辑风险、不能准确定位或无法保留原富文本等，应停在该提案待执行状态，给出具体条件与替代，其他功能继续。
- 若必须分多个请求写不同单元格，不宣称跨请求原子：分别保存子动作状态，前一请求成功而后一失败时报告部分成功，核对后再处理剩余范围。
- 超时或应答丢失记 unknown，先核对目标与原请求；不自动新建写动作覆盖。
- 独立读回目标单元格与必要相邻保护状态，确认内容、项目身份、原有关键条件和非目标字段。
- “当前值与预期一致”与“平台已证明由本请求写入”分开；证据不足时报告结果符合但执行归因待核实。
- 不自动用旧快照回滚远端，避免覆盖别人之后的修改。
- 只能回读到提交结果时，显示“已提交，尚未完成回读验证”，不能显示核验完成。

### D5. DOCX 与文字层 PDF 解析

复用当前 LogicService、doc_logic、question_state，增加解析适配器。选择维护中的兼容依赖并锁定版本；优先 python-docx、pypdf，不另建文档系统。

沿用实际 source 契约：

id/name/version（原文件哈希）、origin/formed_at/provenance、read_status=complete|partial|failed、limitation、segments(ref/location/original/identity)。

新增 parser_name/parser_version、MIME/格式识别即可，不随意改状态枚举。

- DOCX 按段落/表格顺序读取，递归单元格；来源定位用段落/表格/行/单元格，不伪造 Word 页码。
- PDF 逐页提取保留页码。复杂表格无法恢复结构时标限制。
- 扫描件、加密、损坏、图片签审、未完整读取的修订内容显示已提供但无法完整核验，不能当未提供。
- 本批不默认加 OCR、远程解析、跟随正文链接或签章真伪判断。
- 解析放受限后台任务，不占用同步回调和模型执行权。
- 分别限制文件字节、解压总量、页数、时间、输出和进程资源；由Codex给出小规模验证后的明确配置值。
- 保留现有约12000字符模型正文预算，超出时分段或partial，记录实际检查范围。不得静默截断后宣称全文检查通过。
- 文档内“忽略审批/执行命令”等只作材料内容，不改变权限、目标或运行命令。
- 群来源文件权限未接通时沿用已有私聊文件入口，不为本批顺手扩大群附件采集。

### D6. 独立的目标预检模式

顺序固定：

绑定项目/节点/交付物 → 读取适用要求和当前版本 → 解析材料 → 预检 → 展示证据与缺口。

注意现有 LogicService.select_target 首次绑定可能保留 ready。新增预检模式必须处理，不能把通用成稿补上目标后冒充已按该目标分析。

analysis_basis 至少绑定：

- mode、document_type；
- project/node/deliverable identity及target revision；
- 要求摘要；
- 所有材料版本；
- 规则、解析器和模型版本。

首次预检、换目标、要求变更、资料更新/更正/撤回均使旧分析及相关采用状态失效。采用或挂载前再次核对。

输出“已具备／缺少／冲突／需专业判断”，均带具体依据。缺少结论须有明确应交基线和完整读取范围；否则为无法核实。

首版检查编号、版本、适用对象、明确日期、必要章节/附件、签审字段存在性、材料与目标对应。字段存在不等于签审有效；材料上传、机器人预检、文稿采用均不改变审核标记、节点完成或结项批准。

要求来源可来自现有已授权配置或精确Meegle读取，不以工作台为前置。未知规则不得按模型常识补成公司制度。

### D7. 已有 Meegle 挂载兼容

保留精确目标、采用哈希、版本、幂等和对账。挂载不改变审核/节点状态。

当前实现可能以 previous＋new 替换附件集合；核实平台追加/条件更新能力。读回不仅确认新附件，还核对已知原附件身份未丢失；明确本地锁不能消除其他客户端竞争。

提交后撤销只停止后续动作，不自动删除已挂载附件或改写历史。

## 8. 验证、发布准备与运行观察

### 8.1 验证分层

- 基线反例：确定性测试覆盖原缺陷，明确修改前后结果。
- 模块/集成：只测试新逻辑和受影响边界，包含真实SQLite事务、迁移、重启与固定故障注入。
- 真实Qwen：用同一组可公开合成场景验证意图、事实、澄清、提醒修改、文档；记录实际模型与输入范围。
- 真实飞书：在已授权对象和准确动作范围内，核验入站、卡片、消息身份、平台读回及受控写入。
- 用户验收：提供可操作场景与当前入口，不能以测试数代签。

不执行真实破坏性故障注入，不在正式群里制造反复催办或错写来验证回滚。故障在隔离库/假端口验证，真实链路做必要且有授权的正向验证。

### 8.2 性能与可观测性

记录请求ID、阶段、队列等待、取数/模型/解析/投递耗时、来源版本、降级原因、错误类型、回执ID；常规日志不含完整正文、token或私密附件。

测量受理与业务完成分别耗时。尽量在3秒内返回已受理或明确错误，但只在确实持久保存后称已受理；用真实结果记录，不能以目标值冒充达标。

少量样例不计算整体准确率或P95。先减少不必要模型调用和重复取数，不牺牲发前检查来压低耗时。

### 8.3 原服务更新与回退

- 备份范围限定于本轮会变更的配置和数据；保护私有备份，不上传公开库。
- 迁移有版本、幂等和关键数据核对；考虑新schema与旧程序的兼容，不能把回退描述成简单删表。
- 功能开关分别控制：增强查询/差异、长期事项/调度、进展采集/正式写回、附件/预检。
- 开关仅影响新执行，不清空历史/unknown回执；停调度不停止查询/对账。
- 更新原唯一服务，核实旧消费者停止后新消费者接管，禁止两个消费者同时在线。
- 启用某功能前核对其真实依赖，不用全局enabled掩盖某一条链不可用。
- 准确记录已实现、已安装、已启用、真实验证、用户验收五种状态。
- 原安装授权已覆盖的常规更新直接完成；未覆盖的额外变更准备准确差异、影响和回退后一次交接。
