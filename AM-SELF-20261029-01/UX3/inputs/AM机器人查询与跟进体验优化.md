## 四、第一阶段：打通普通员工的私聊查询

### 4.1 分开三种能力

实现明确的能力判断，可按工程习惯命名，但语义必须分开：

| 能力 | 可做什么 | 不能因此获得什么 |
| --- | --- | --- |
| `query_read` | 查看本人获准的项目目录、详情、查询候选、最近查看记录和来源链接 | 跟进管理、群发送、订阅管理、资料挂载或正式台账写回 |
| `feedback_assignee` | 对本人被指定的具体事项提交反馈，处理对应私聊补填卡 | 修改他人反馈、负责人决定、事项管理和项目权限 |
| `owner_manage` | 项目负责人管理跟进事项、计划、提醒、收集和内容确认 | 自动启用台账写回或跳过准确发送批准 |

不要简单删除全部 `OWNER_ONLY`。先列出需要开放的只读动作白名单，再逐一接通入口、数据过滤、卡片回调和投递授权。管理动作继续服务端校验 owner，不能只靠隐藏按钮。

### 4.2 复用已有身份与数据范围

1. 复用当前可信 app、tenant、open_id、在职状态和 TH2 部门/子部门核验。姓名不能授予权限。
2. `authorize_user()` 只证明身份资格；项目可见范围仍需从实际已批准的数据范围取得。
3. 先核对运行配置是否已有明确的私聊项目范围或用户范围。存在时直接复用。
4. 若现有权限只按群维护，核对能否复用“用户当前所属、已批准披露群”的项目范围，形成该用户私聊可查看集合；保留群成员与披露范围变化的影响。不能把某个群的批准自动扩大为整个租户可见。
5. 若现有批准明确仅限群内展示，无法据此形成私聊范围，先完成其余代码与合成验证，在交接中只列出具体缺失映射及建议值，例如“哪些现有成员可以在私聊查看哪些现有项目”。不要扩大为全租户、全台账或全部 PoC 工具权限，也不要让这一个待决定项阻塞其他工作。
6. 原 PoC `config.users` 继续控制原文档/模型工具等能力。只读查询应有独立投递鉴权，不通过批量添加 PoC 用户来实现。

同一权限结果要覆盖目录、搜索候选、项目总数、页码、最近查看、详情、来源链接和投递。不要在正文过滤后仍泄露无权项目的名称、数量或链接。

### 4.3 修复入口静默吞掉

调整 AM 与旧路由的认领规则：

- 合法的项目只读请求进入新的 `query_read` 链路。
- 合法的管理请求按 `owner_manage` 处理；普通员工误触时给简短、可理解的提示及可使用的查询入口。
- 不属于本模块的输入返回未认领，允许原有正确路由继续工作。
- 已识别但无权执行的动作不继续交给普通模型猜测处理；给有限且不泄露数据的说明。
- 被拒绝、路由未匹配、已处理、资料暂不可用要有不同的内部状态；用户文案使用正常语言。
- `/menu`、`/am` 和常驻入口应按当前用户能力进入合适页面，不能对普通同事静默结束。
- 保留原自然语言直接提问，例如“某项目谁负责”“某项目下一步做什么”；明确项目与字段时零新增模型调用。歧义给出获准项目的可点候选，不要求先学习命令。
- 不把所有包含“如何”“怎么样”等词的普通聊天一概吞进 owner 专用链路；对确定性分类边界做定向验证。

首次进入及主动重开菜单应生成或恢复本人的导航卡；不要通过主动给所有同事发卡来完成“员工首页上线”。

首先保证用户点击既有常驻入口或发送“项目”等明确指令时可达。若要在用户仅打开私聊窗口时自动展示，先核实当前平台事件、应用订阅及授权是否支持，不能凭界面打开推断服务会收到事件。若常驻菜单不能按用户角色配置，复用共同入口并在服务端按能力返回不同页面，不把个性化底部菜单作为前提。

### 4.4 私聊卡片隔离

复用现有 `scope = tenant + app + chat + user (+ thread)`、interaction、view version、nonce 和消息绑定。每个人维护自己的导航与最近查看记录。卡片内容、页码、搜索条件、当前项目及回调不能串到另一个人或另一个聊天。

菜单事件缺少 chat_id 时，沿用真实消息回读绑定方式。不得伪造工程师发言或冒用他人身份测试。复制他人卡片、重放旧按钮及跨话题操作应保持正确拒绝或恢复行为。

## 五、第二阶段：项目列表、短路径和卡片外观

### 5.1 普通员工默认首页就是项目目录

页面标题建议为“项目查询”。首屏直接展示可查看项目，默认每页 5 项；项目不足 5 项时全部展示。

每个条目显示：

- 项目名称，必要时附便于区分的编号；名称为主要视觉内容。
- 可由来源明确证明的负责人、当前阶段或状态，最多一行辅助信息。
- 资料不含负责人或阶段时标“未记录”，或省略对应字段；不要通过模型猜一个状态。
- 一个明显的进入项目动作，避免同一条目再套“查看详情—更多—栏目”等空层级。

搜索保留为辅助功能：空搜索仍显示目录，清空后回到合理页码；默认不要求输入名称或编号才能看到项目。返回目录保留原筛选、页码和排序。

增加“最近查看”作为便利入口，记录仅来自本人已成功打开的项目。每次展示仍应用当前可见范围。不要记录私人聊天正文用于推荐。

“我的项目”不作为本轮上线前提。只有已有可信的人员 ID—项目关系时才启用；无可靠映射时用可查看目录与最近查看解决入口问题。不要按姓名字符串猜归属，不要求人工维护一套重复项目成员表来完成第一阶段。

### 5.2 项目详情去掉空中间页

项目详情上方固定显示名称及必要身份信息；正文默认显示简短进展，直接提供“进展 / 人员 / 计划 / 待办”四个栏目入口。“计划”展示来源已有关键日期及依赖，不伪造 WBS 或排期。

具体要求：

- 删除查询路径中的“查看栏目”和“项目操作”空中间页。
- 负责人能可靠短显时，在项目摘要中直接显示；否则“人员”一次点击可达。
- 从目录进入项目只需一次点击，进入人员/计划/待办最多再点一次。
- 查询“谁负责”只回答对应人员与必要职责、限定条件，不附上整段无关进展。
- 多字段问题逐项回答已问字段；超出卡片预算时明确说明可展开内容及原文入口，不能静默丢字段。
- 原文较长或条件不可安全拆分时，显示明确的短说明并提供完整内容，避免把“尚未验收”“完成某测试后再决定”等条件截掉。
- 来源时间和资料读取时间分开；“读取于某时刻”不能变成项目在该时刻更新、完成或验收的证据。
- 页面底部提供“返回项目列表”和必要的“刷新资料”；来源链接作为辅助入口。

项目负责人在同一个项目详情中可看到“发起跟进”或对应人员处的“提醒负责人”，两者复用同一跟进表单与准确预览流程；普通员工看不到该管理入口且服务端仍拒绝直接构造相应动作。

### 5.3 视觉约束

使用现有飞书原生卡片能力，先以真实客户端支持为准：

- 白色/中性底色、清晰标题、克制的强调色与留白；不要把普通列表染成多种状态色。
- 只有当前主要操作使用强调按钮，其他导航用较轻样式；不用一列等权重大按钮堆满页面。
- 每个项目条目保持统一的名称、辅助信息、动作位置。
- 分页控件固定在列表底部，展示经过权限过滤后的页码与数量；无上一页/下一页时使用明确不可用状态或不显示。
- 普通首页不展示模型、数据库、台账写回开关、诊断代码、任务编号等实现信息。必要诊断留在 owner 的维护入口。
- 操作状态只显示与用户当前动作有关的信息，例如“资料读取中”“已提交反馈”；不要同时铺开多个系统状态区。
- 表单保持手机单列可用，长名称正常换行；不要依赖桌面多列宽度才能理解。
- 每次导航复用本人的同一张导航卡；反馈回执、准确预览等有独立业务含义的卡片按原语义保留，不混成一张不断变内容的批准卡。

旧卡片保留历史证据，不批量删除聊天消息。用户从常驻入口重新打开时，应明显知道哪个是当前入口；过期或旧版本按钮提供清晰恢复路径，不无限新增恢复卡。

本轮配套可点击布局预览仅用于检查信息结构、按钮位置和操作路径，使用演示数据。本地 HTML 的瞬时切换不是飞书 API、真实卡片回调或客户端速度实测，不能据此宣布 3 秒目标已达成；真实客户端兼容、手机与真人业务体验仍按本稿验收要求执行。

聊天中的交互示意是参考素材，不是必读附件。本稿中的文字规格已经包含实施要求；执行端读不到示意时可以继续，不要求项目负责人另行搬运文件。

## 六、第二阶段同时完成：减少远端等待

### 6.1 确定性浏览全部走代码

目录、搜索、分页、返回、字段切换、状态筛选、项目匹配和固定事实渲染均不调用 Qwen。保留原模型用于确实需要语言理解或整理的任务；不得为普通导航新增推理调用或排队等待模型。

不将“唯一事件消费者”理解为所有网络 I/O 必须在同一循环同步串行完成。可在原消费者内使用有界工作任务处理读取与核验，但不能启动第二个飞书消费者或第二条模型推理通道。

### 6.2 引入可复用的资料快照

复用现有 project catalog / source baseline 能力，增加或整理只读快照接口，至少包含：

- 来源身份与完整读取范围。
- 快照 `version`。
- `observed_at`，代表本次成功读取时刻。
- 来源自身 revision / 更新时间（来源提供时）。
- 完整性状态与读取限制。

本轮默认工程参数建议：活跃使用期间每 60 秒刷新一次；5 分钟作为软过期阈值。它们是可调整的初始实现值，不是已经达成的业务时效承诺。将参数集中配置，按真实源响应和用户使用情况调整，不散落在各个按钮处理函数里。

行为要求：

1. 首页和查询从最近成功快照进行授权后投影。
2. 同一快照上的热缓存翻页、返回、字段切换不重新读取台账。
3. 同一资料源的并发刷新合并为一次在途读取；其他请求复用可用快照，不为每个用户独立重新拉整表。
4. 快照超过软过期阈值时，清楚显示上次读取时间并提供刷新；允许展示时不得自称“最新”。无法确定可安全展示或资料不完整时，给明确限制及恢复动作。
5. 首次无可用快照时异步读取，显示有界读取状态；不要用空列表冒充“没有项目”。
6. 读取失败保留上次成功快照及失败状态，不能用半页或空响应覆盖完整目录。局部读取不能据此断言项目被删除。
7. 当前页绑定快照版本，连续翻页使用稳定排序；刷新换版本时保持可解释的当前位置或返回列表，不能使条目跳转到另一个项目。
8. 项目状态展示引用原事实。快照取得时间不等于业务事实产生时间，更不等于完成或验收时间。

### 6.3 数据缓存不等于授权缓存

资料可缓存；身份和项目可见范围不能因此永久放行。保留发布前的当前撤权校验与原有效约束。旧卡片、旧列表、最近查看、历史搜索和缓存命中都不能绕过撤权。

可以整理同一只读请求内部重复校验，但不得为追求 3 秒而直接取消交付前核权。若当前可靠的身份/撤权核验无法稳定落入性能预算，应如实计入鉴权耗时，继续做其他减少往返的优化；不要把放宽权限偷偷变成性能修复。

### 6.4 卡片回调直接返回：先验证，再采用

将“在卡片回调响应中直接返回下一张卡片”作为受测优化候选，目标是减少额外 PATCH 往返，不预先假定当前 SDK、卡片版本和事件通道都支持。

实施前核实当前飞书官方协议、SDK 版本、回调响应结构及 3 秒约束，并做一个仅涉及本人只读导航的最小验证。记录能否更新当前卡、卡片版本如何绑定，以及成功回执代表什么。

- 本地快照、当前权限及卡片计算能在回调预算内完成时，才考虑直接返回卡片。
- 任何需要慢网络鉴权、慢源读取或等待模型的路径，继续使用异步处理。
- 不在事件线程中等待远端操作而阻塞其他事件；及时响应只能说明已受理，不能把 toast 当作结果已经可用。
- 如果直接返回卡片不能满足权限、版本或可验证交付要求，保留现有可靠异步路径，并在交接说明实测结论。

同步响应的“已经返回”不自动等于卡片“已经在平台应用”。为该分支单独记录可靠发布证据及待核验状态，避免同时直接返回卡片又排队 PATCH 同一版本，也不得因响应结果未知重新执行业务动作。

官方能力依据：[回调概述](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/callback-overview)确认回调可返回更新后的卡片；[旧版按钮说明](https://open.feishu.cn/document/common-capabilities/message-card/add-card-interaction/interactive-components/button?lang=zh-CN)说明立即响应与超时约束。实施时以当前[处理卡片回调](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/handle-card-callbacks)协议及实际 SDK 验证结果为准，不照搬旧版响应结构，不将平台 3 秒响应时限等同于客户端可操作结果的 3 秒目标。

### 6.5 完整回读移出前台串行等待

现有导航投递后的完整回读可能阻塞后续请求。将只读导航的核验安排到独立、有界 I/O 任务中，使用户后续浏览和其他用户请求不等待该任务完成。

必须同时满足：

- 不取消核验，不把未核验写成已核验。
- 分别记录发布成功、核验成功、核验失败、发送结果未知。
- 同一张卡片的发布保持版本有序；晚返回的旧请求不能覆盖新页面。
- 旧版本回读在新版本发布后才完成时，只能用于对应版本的状态处理，不能把新页面错误回滚，也不能把旧版本误判成未发送并补发。
- 不同用户、不同导航卡互不串行阻塞；并发量有上限，避免无限线程或请求堆积。
- 超时、重试及退避有界；结果 `unknown` 仍保持未知，不能按“未发送”创建重复消息。
- 准确预览、批准、真实群发送、反馈落账等业务语义不得被普通浏览优化覆盖。

### 6.6 性能目标与记录口径

目标为真实平台常见只读浏览的可操作响应 P95 小于 3 秒；这是本轮优化目标，不能在实测前保证达成。客户端屏幕未观测时，不得用服务器回执代替“用户已看到”。

至少分开记录四个时间：

| 时间 | 含义 |
| --- | --- |
| callback | 入站到回调响应；说明受理是否及时 |
| publish | 入站到卡片首次成功发布/更新的可靠回执；作为服务器侧可操作结果指标 |
| client | 实际客户端出现可操作结果；无法自动测量则用明确的人工观测样本，不编造 |
| verify | 对应发布版本完成独立回读核验的时刻 |

另保留排队、处理鉴权、资料读取、本地计算/渲染、交付鉴权及 CREATE/PATCH 等分段。包含子段的总耗时不能再与子段相加。先证明哪个环节减少了调用或等待，再描述效果。

每份结果标清样本数、冷/热条件、命中状态、代码版本及失败样本；报告中位数、样本 P95 和最大值时注明样本规模。约 30 次只能提供本轮观察，不能冒称长期稳定 P95 或推断整个平台的性能。

## 七、第三阶段：项目负责人的跟进体验

员工查询闭环可用后，复用原跟进事项、提醒计划、准确预览、反馈和幂等能力，调整项目负责人的入口与页面。

### 7.1 个人入口

项目负责人仍能直接进入项目目录，同时有清晰的“我的跟进”入口。跟进列表分为：

- 待我处理：有新反馈、需要协助、提交材料待核验，或有尚待项目负责人完成的明确动作。
- 等待反馈：已发出或已安排、当前等待负责人反馈的有效事项。
- 已关闭：已按原规则关闭或取消的历史事项；状态含义不能混淆。

筛选由现有真实状态和事件记录推导，并在代码中集中定义。不要凭最后更新时间猜“已处理”，不要把草稿、等待发送或发送未知混为“已发出等待反馈”。发送未知要在具体事项上显示待核对，保留原恢复入口。

列表条目优先显示项目、事项短标题、当前状态、负责人和下一次需要处理的时间；有新反馈时用简短提示，点击查看完整反馈。首页不混排台账候选待办和已正式建立的 AM 跟进事项；台账待办在项目页可查看并发起跟进。

### 7.2 发起跟进路径

目标路径：项目详情 → 发起跟进 → 单一表单 → 准确预览 → 确认。

表单尽量在一个页面内完成：

- 项目固定绑定当前稳定项目身份。
- 事项内容。
- 已获准可选负责人。
- 目标群或当前允许的接收方式。
- 需要反馈的时间或下一次跟进时间。
- 发送方式及时间；可直接复用现有默认值，但默认不等于批准。

只预填来源或已有记录能够证明的信息。搜索负责人、选择群、修改时间返回表单时保留有效输入，不让用户重复填写。取消只结束当前草稿，保留已有业务记录。

确认前必须展示准确接收对象、完整正文、时间及本次动作的具体影响。预览内容变化后原确认失效；“确认内容”不生成正式台账写入批准。确认后沿用既有幂等和发送回执语义，不重复发送。

如果仅建立跟进事项而不对外发送，页面明确显示结果；如果包含群消息或对他人私聊发送，继续按原准确预览和有效授权执行。不能因为项目负责人点击项目页“发起跟进”就自动发送。

### 7.3 反馈处理

继续使用现有负责人反馈身份、独立反馈代次、补填卡、通知去重和迟到反馈留证。调整展示时不能丢失原事项、原消息、原群和原版本关联。

工程师的反馈入口只要求本次必要内容；预计日期漏填后保留有效说明，补齐即可。项目负责人从新反馈提示进入对应事项，查看、核验、继续跟进或关闭均遵守原业务规则。不要把工程师“已提交材料”直接显示为“事项已验收”。

## 九、验证与完成标准

以用户能完成任务和真实链路为主，不以“检查项数量增加”替代验收。复用对应代码版本的历史有效证据，只补受本轮影响的边界和行为。

### 9.1 必须覆盖的场景

| 场景 | 可观察结果 |
| --- | --- |
| 普通已授权员工、不在旧 PoC 白名单 | 可以从私聊菜单进入项目目录、打开详情、查询负责人，结果能真实通过新的只读投递路径；没有获得管理或文档工具权限 |
| 普通员工直接问项目问题 | 不被 owner 路由静默吞掉；明确对象直接回答，歧义给可点候选 |
| 非授权或已撤权用户 | 没有获准项目内容、名称、计数、最近访问或链接泄露；旧卡和缓存不绕过撤权 |
| owner 和员工使用同一功能 | 查询数据范围正确，导航、分页、最近查看和回调互不影响；员工构造管理动作仍被拒绝 |
| 打开目录且不输入关键词 | 直接看到可查看列表，每页默认 5 项；搜索和清空后结果正确 |
| 目录进入项目并查人员/计划/待办 | 一次进入项目，最多再一次进入常用栏目；不再经过“查看栏目/项目操作” |
| 热缓存连续翻页/字段切换 | 新增模型调用为 0，同一快照不重新读台账；有稳定的快照版本和排序 |
| 资料刷新慢或失败 | 旧快照时间与限制清楚；首次无快照不显示假的空目录；其他人的浏览不被拖住 |
| 慢 PATCH、慢回读、快速连续点击 | 旧结果不覆盖新页面，同卡有序；其他用户独立，回读状态真实，未知结果不重复发送 |
| 来源含预计、取消、依赖、未验收、多型号等条件 | 查询短答和详情保留完整必要限定，不能提速后丢事实边界 |
| 项目负责人发起跟进并修改表单 | 既有项目身份正确，输入保留，准确预览对应本次内容；改变内容必须重新确认 |
| 工程师反馈及补填 | 原绑定和去重有效，补填不丢说明，重复点击不增加业务反馈或通知 |

双身份并发使用隔离合成身份和合成数据验证，不在真实服务伪造他人身份。真实工程师行为必须由该工程师本人操作；没有真人验收就标待验收。

### 9.2 性能观察

安排约 30 次与本轮有关的只读浏览观察，覆盖首页、目录、连续翻页、返回、项目详情、字段切换和主动刷新，区分热缓存与首次无缓存。保留慢请求和失败请求，不只挑最快的样本。

其中真实平台观察限于实际获准、可操作的账号与场景；本人可以完成的路径先完成。另用隔离合成场景验证双身份并发、慢源、慢 PATCH/回读及乱序，不把合成速度填成真实平台成绩。

结果至少给出：每步远端调用次数、是否读取台账、是否调用模型、关键分段耗时、四类时间口径、样本数、代码版本及限制。若仍未达到 3 秒目标，明确尚慢的环节和已完成的改善；不要用“受理小于 3 秒”代替“结果小于 3 秒”。

### 9.3 真实客户端验收

实际查看桌面卡片的列表、长名称、项目详情、返回及表单。手机在有实际可用条件时直接验证；没有条件就交一份简短操作清单并标待验证，不用桌面截图推断手机通过。

不为验证制造真实业务群发、提醒、订阅或挂载；相关写操作先用隔离合成验证。真实业务外发必须有原有效授权与准确预览批准，不能由本稿代替具体发送批准。

### 9.4 完成判据

第一阶段不能仅凭 owner 测试通过判定完成。普通员工从入站、可见目录到投递的闭环必须有对应证据；若真实私聊数据范围有具体未决映射，要明确说明合成完成范围及实际启用条件。

2. 列表优先、搜索辅助，常用栏目短路径可达；页面内容和视觉规则在实际客户端可用。
3. 热缓存浏览零新增模型调用，不因翻页或切字段重复读取台账；权限校验没有被缓存绕过。
