## 三、F08 最小补修

### 3.1 确定反例

真实 DOCX 表格一行四列：

| 列 1 | 列 2 | 列 3 | 列 4 |
| --- | --- | --- | --- |
| 交付物清单 | 空白单元格 | 负责人 | AR001合成人员 |

解析器正确跳过空单元格，保留列 1、列 3、列 4 的位置。当前 substantive_requirement() 扫描同一行全部后续 segment：跳过“负责人”标题后，把第四列姓名当成清单内容。

当前输出：

~~~json
{
  "已具备": [{
    "finding": "交付物清单：找到实质条目或字段值，含义与有效性仍需核验",
    "refs": ["S1:1", "S1:3"]
  }],
  "缺少": []
}
~~~

S1:3 实际位于第四列，是负责人姓名。完整可读不等于字段关联成立，该证据不能支持空清单。

定位：[precheck.py 的 substantive_requirement](https://github.com/Catcherog/project-workbench-review/blob/9c57f3197bc901df2d582662249cac6d25294bbe/AM-SELF-20261029-01/R1-FIX1/source/FS-AGENT-GROK-POC-20261017-01_R1_Studio/src/fs_agent/precheck.py#L23)。

### 3.2 正确行为

- 按明确结构将标签绑定到对应值单元格或同一内容区域；空值不能跳过其他字段得到“补值”。
- 遇到下一个独立字段标题，结束当前字段取值。
- 合并单元格或结构关系不明时，保留“需专业判断”，不能仅凭同行有文字认定已具备。
- 完整读取且能确认对应值为空时，判为缺少；不完整读取保持无法核实性质。
- 不采用“整行有任何文字即具备”或无限扩充标题黑名单的补丁。

### 3.3 最小正确断言

在第 2.3 节所述独立环境执行：已注册本次 FIX1 的 fs_agent 及锁定依赖，并确认 python -I 子进程加载的 attachment_worker 属于本审核副本。仅设置 PYTHONPATH 不足以满足实际 DOCX 解析器的隔离调用。

~~~python
import io
from docx import Document
from fs_agent.doc_logic import read_source
from fs_agent.precheck import inspect_materials

requirements = {
    "checks": [
        {"id": "1", "label": "交付物清单", "text": "交付物清单", "kind": "presence"}
    ]
}

def inspect(cells):
    doc = Document()
    table = doc.add_table(rows=1, cols=len(cells))
    for index, text in enumerate(cells):
        table.cell(0, index).text = text
    content = io.BytesIO()
    doc.save(content)
    source = read_source(
        "synthetic.docx", content.getvalue(),
        source_id="S1", origin="synthetic"
    )
    assert source["read_status"] == "complete"
    return inspect_materials([source], requirements)

positive = inspect(("交付物清单", "测试报告A"))
assert positive["已具备"], "明确对应值的正对照应通过"

empty = inspect(("交付物清单", "", "负责人", "AR001合成人员"))
assert not empty["已具备"], "空清单不能借用后续负责人字段"
assert empty["缺少"] or empty["需专业判断"]
~~~

FIX1 上“不归为已具备”的断言失败，有实质内容的正对照通过。修复后保留该反例、二列正例及既有 F08 空值、不完整读取测试，执行受影响的预检回归即可，不追加无关全量重审。

## 四、UX1 产品方案

### 4.1 统一入口

原 AM 私聊底部设置三个常驻一级菜单：

| 菜单 | 页面 |
| --- | --- |
| 我的工作 | 工作首页卡，聚合日常入口 |
| 项目 | 项目选择、查询与详情 |
| 更多 | 提醒计划、简报订阅、运行状态与帮助 |

首次使用者点菜单即可开始。已有 /menu 改为同一张工作首页卡；命令继续调用相同业务能力。用户也可以直接说“查需求75的进展”，日常流程不依赖记命令。

首页最多放六个清楚的入口：**项目查询、待办与跟进、创建提醒、变化简报、更新进展、资料预检**。按当前用户权限与实际启用功能展示，不可用项给出明确原因或不展示。

### 4.2 对象随操作传递

选中项目后，后续卡片自动带入该项目。用户看到项目名称、事项名称和时间，不需要输入内部 ID、版本号、nonce 或分隔符。

项目卡显示当前进展、责任人、关键日期、待办以及必要来源/读取时间；资料不足、读取失败与真实没有待办要区分。保留“查看依据”，不把技术诊断信息铺满首页。

同名候选提供可区分信息供选择；未核实候选不能直接形成新的真实项目绑定。引用聊天继续遵循 F03 规则。

### 4.3 日常路径

| 用户目标 | 卡片与输入路径 | 完成反馈 |
| --- | --- | --- |
| 查项目 | 项目 → 选项目或输入关键词 → 详情 → 日期/人员/待办/依据 | 最新读取结果与来源 |
| 看自己的工作 | 我的工作 → 待办与跟进 → 事项详情 | 待办、反馈明细及下一次检查时间 |
| 发一次提醒 | 创建提醒 → 项目、授权群、对象、正文、时间 → 完整预览 → 确认 | 已发送、确定失败或结果待核对 |
| 建提醒计划 | 更多 → 提醒计划 → 填规则 → 实际时间与窗口预览 → 确认 | 计划状态与下一实例 |
| 反馈事项 | 原事项卡 → 收到/预计时间/需要协助/提交材料/非本人负责 | 必要内容在表单填写并记录到该事项 |
| 采集进展 | 更新进展 → 选项目 → 当前聊天直接发自然语言 → 核对采集内容 | 待核对提案，正式写回仍未开启 |
| 资料预检 | 选项目/节点/交付物与应交要求 → 当前聊天发附件或原文 → 预检 | 已具备、缺少、冲突、需专业判断及证据 |
| 看或订阅简报 | 查看变化简报；更多 → 订阅 → 范围/时间 → 预览确认 | 查询结果或订阅状态 |

文字与附件沿用聊天输入；卡片负责选择对象、显示进度和确认下一步。对象选好后直接发送自然语言或文件即可继续，不再输入命令和技术编号。

上下文必须可见，例如“当前收集：需求75 / 试验报告”，并提供更换对象、取消收集。上下文过期、冲突或存在多个候选时让用户点选，不能暗中套用最近项目。

### 4.4 提醒与计划预览

完整显示项目、事项、目标群、涉及人员、实际正文、发送时刻与时区、有效窗口、周期规则、是否还需逐次批准。时间采用原业务时区；跨日、周期和时区转换时显示具体日期。

普通周期的日历按原规则核实；没有可靠日历时给出可执行说明，不自动把周一至周五当作工作日日历。

修改时保留已填草稿；确认仅批准当时完整呈现的版本。目标、正文、时刻或规则变化后原批准失效。unknown 只提供“核对发送结果”，不提供会造成重复外发的一键重发。

### 4.5 工程师反馈

工程师在既有授权事项卡上操作：

- 已收到：记录收到，不自动标为完成。
- 预计时间：选时间并补充说明。
- 需要协助：填写阻碍和需要的帮助。
- 提交材料：填写材料链接或进入已绑定事项的聊天补充流程。
- 非本人负责：记录事实，交由负责人处理分派。

沿用 F02 决定版本。同一人可先收到、再报时间、再提交；多人分别反馈互不阻断。人工暂停、关闭或改变决定后，旧反馈不能覆盖新决定。本人详情可看有效及迟到反馈的正文、时间、来源和材料。

私聊导航与群内共享事项卡分别处理。能点工程师反馈卡不等于拥有项目经理首页的全部权限；群卡刷新不能把个人项目列表展示给全群。

### 4.6 状态与下一步

| 内部情形 | 用户看到的状态与下一步 |
| --- | --- |
| 请求入队 | 已收到，正在处理 |
| 业务完成且有依据 | 已完成，并显示具体结果 |

浏览、翻页、选对象不弹业务批准确认。真实外发、规则批准、挂载及精确字段写回保留完整预览，不能把“下一步”变成意外外部执行。

8. 收集上下文保存用户、聊天、话题、明确目标与期限；过期或歧义时澄清。附件不能误归给另一个用户、话题或旧项目。
