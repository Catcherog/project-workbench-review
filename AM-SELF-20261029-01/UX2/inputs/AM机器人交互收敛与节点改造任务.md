## 1. 本轮要解决什么

项目负责人对已发布 AM 1.0.13 的实际反馈是：UI 不够简洁，信息同时出现太多、太杂，希望 Agent 有更清楚的执行节点，使操作容易、输出稳定、内容可控。

本轮沿用现有业务能力，统一任务编排与分步交互：先判断当前任务，绑定正确对象，补齐真正缺少的输入，执行需要的内部步骤，再只呈现用户当前需要理解或决定的内容。完整业务记录、证据、准确批准对象仍可访问。

完成后应能看到以下变化：查询所问即所得；普通导航在一张当前私聊卡内前进和返回；一次动作通常得到一份可见结果；历史不反复重放；不同任务的结果不抢占彼此页面；出错时能知道下一步；无须记命令便能使用高频功能。内部可以有多个节点，但不能把每个节点都变成一次用户确认。

## 3. 先修的源码问题

以下严重性针对本轮体验，不改写项目原来的 P0—P4 业务优先级。B 表示 source/local-qwen3.8/feishu-bridge/；F 表示 source/FS-AGENT-GROK-POC-20261017-01_R1_Studio/src/fs_agent/。行号用于定位此固定快照，执行前以实际函数为准。

### A 类：先修确定性错误和结果不一致

1. **项目栏目枚举错配。** B/am_ux.py 的 ux_project_detail() 约 108—116 行传“关键日期、人员与职责、待办”等中文字段，B/group_ledger.py 的 render_project() 约 144—160 行按 schedule、people、todo 判断，导致多个栏目按钮均重复进展。统一一个字段枚举及栏目模型；区分 None、显式空列表和单栏目选择。概览、日期、人员、待办、来源必须拥有各自视图，“查看依据”不能通过空列表回落成进展。

2. **简洁摘要与依据校验互相冲突。** B/group_ai.py 约 267—269 行要求摘要且不重复原文，validate_grounded() 约 133—139 行却要求文本等于完整字段、引用字段全部证据。正常摘要被拒后，又回整字段原文。不得以删除严格 grounding、仅检查 evidence ID 存在的方式修复。先按第 6 节落地完整语义块的抽取式短答，再考虑经验证的事实结构化；无法安全缩短时给短提示和原文入口。

3. **订阅承诺与投递内容不一致。** B/am_ux.py 约 450、462 行承诺“项目变化及待办”，B/am_business.py 的定时 payload 约 119—129 行只列变化；主动简报 B/am_service.py 约 275—286 行才附待办。统一 BriefingData：订阅预览、计划详情、实际投递均从同一数据约定生成。保留主动查看不消耗订阅投递记录的规则。

4. **业务幂等尚不等于通知幂等。** F/action_items.py 的 feedback() 对重复业务事件可返回原结果，但 B/am_business.py 的 handle_feedback() 仍继续通知反馈者与 owner。为每个可见通知建立稳定业务事件键，验证同事件重放和独立重复点击都不会重复制造通知；不得只凭事项没有重复记录就判通过。

### B 类：直接造成长、杂、重复的呈现问题

5. **只问一个字段仍附完整进展，多项目再重复拼接。** render_project() 无条件带进展，group_ai.reply() 的明确编号路径逐项目拼接完整答复。字段选择先于渲染；多项目用一张短列表，不循环发送完整详情。缺失编号、重复编号也以有界条目显示，能进一步展开。

6. **普通导航每步新建消息。** ux_page() 调 notify()，Store.add_outbox() 每次生成 UUID，Feishu.send() 调 create；update_multi=true 并未自动实现原卡更新。增加当前私聊视图的 message_id 和版本，按第 7 节实现更新与恢复。

7. **反馈与详情不断重放全部历史。** item_text()/ux_item_text() 默认展开全部历史，每次反馈又把完整事项通知 owner。改为新增变化通知、当前状态摘要、历史分页三层。保留现有通知时机；先不擅自静默、延迟、合并掉需要及时处理的协助或阻塞消息。

8. **进展收集一次发两份结果。** B/am_ux.py 约 299—301 行发 update_card 后返回文本，am_service.py 约 392—396 行又 notify。统一为结构化结果，由一个发布节点生成一张“已收集/待核对”卡。ledger_write=false 时不展示可执行写回按钮，不能让“批准修改”与实际开关状态矛盾。

9. **一次提醒包含周期字段，预览正文重复。** B/am_ux.py 约 176—184 行一次提醒仍展示周期截止及批准方式；约 212—217 行同一正文同时作为“事项”和“完整正文”输出。默认一次提醒只展示适用字段，完整正文只出现一次；周期分支再展示截止及规则。

10. **分页只分按钮、不分正文。** 待办页把 todos() 的全量正文放在每页上方；翻页只切 AM 事项按钮。改为真正的数据分页，页内正文只对应当前条目。列表不默认同时展开明细。

11. **互斥动作同时出现、相同按钮没有对象辨识。** 暂停与恢复同时展示，多个发送实例均叫“核对结果”。按状态计算允许动作；实例列表显示具体发生时间、状态，点击后才进入该次核对。

12. **简报与预检直接铺报告，靠截断控制长度。** 简报 before/after 全文加所有待办，超过阈值粗截断；预检把依据指纹、四类全部条目、全部来源直接放首屏。先构造摘要数据和详情入口；摘要、证据、批准内容均不从字符串中间截断。

### C 类：影响稳定性的内部组织问题

13. **输出预算不统一。** 提示词字数、JSON schema、Python 校验、原文回退、传输上限各不相同；字段长度上限不能替代用户首屏设计。建立统一契约与规则校验，并覆盖所有降级分支。

14. **群推理同步占用业务循环。** Bridge.process_cycle() 同步调用 GroupLedger.step()，其内部可以运行意图、排序、回答、修复。复用现有任务池，让菜单、卡片和无需模型的业务步骤继续推进；保持一个消费者及一个模型执行通道。不要为了此项开多个 Qwen 并发。

15. **技术状态混入日常界面。** 原始 rule JSON、policy、UUID、source、指纹与合成测试命令出现在普通帮助、计划、事项和状态页。普通界面显示业务状态与恢复操作；诊断信息有明确的维护入口，继续保留可追踪性。

## 5. 统一界面和信息预算

### 5.1 默认首屏

群内常规首屏以约 120—220 个可见字符为设计目标，私聊常规首屏约 180—300 个可见字符。最多 3 个要点、1 个主操作、2 个次操作；列表建议每页 5 项，可按客户端空间在 3—5 项间调整。标题、状态、业务文字和可见链接文字均纳入统计，隐藏 ID 与原始 URL 不用挤进首屏。

这里的 1 主 2 次指业务决策动作；列表对象行、搜索和翻页另行计数，保留真实的总控件数，不能通过改名来规避可读性核验。

这是一组体验目标，不是通过裁剪文本强制满足的硬闸门。目标内放不下时，应减少当前显示的完整条目、分页或让用户展开。用户明确要求详细内容时进入详情视图；必须保留的事实限定不得为达标删除。

准确审批预览属于例外：发送正文、目标、时间、规则、精确修改范围、挂载目标和版本必须完整可查。不能为了字数预算把批准对象藏成不可访问的摘要。长批准预览可以分节、分页，但最终批准绑定的是同一个完整快照；未看完不应因 UI 自动截断导致对象失真。

### 5.2 文案和动作

每张常规卡回答三件事：现在是什么状态；与我相关的变化是什么；下一步可以做什么。没有待决定事项时只给结果，不制造“请确认收到”。入口与按钮使用业务词，例如“查看来源”“继续补充”“结束收集”“核对发送结果”；内部状态码只供诊断。

按钮由当前状态计算。已暂停只显示恢复，正常运行可显示暂停，已关闭不再展示提交反馈的有效主操作。无法执行的动作优先说明现有状态并给恢复入口，不放一个注定报错的按钮。草稿返回修改保留有效输入，返回上级时保留搜索、筛选和页码。

一般任务允许一次输入多个已有字段，系统只追问真正缺失或歧义的字段；不能为了体现 Node 数量而强制用户逐字段点十次。“明天下午三点提醒某项目负责人提交报告”若上下文、人员、时区均已确定，就直接生成完整预览；必要歧义才集中补一轮。

### 5.3 三层内容

内容分为短结果、业务详情、依据与诊断三类，但不强制用户逐层点击。详情、历史、来源可从当前卡直达，技术诊断仅放维护入口。默认首屏只展示短结果与当前动作；完整信息随时可查，返回后仍保留原任务、对象和有效草稿。

### 5.4 三个输出示意

以下均为合成示意，不表示当前真实项目、人员或检查结果。按钮名称代表设计要求，并非本文件可执行操作。

若读取不完整，主结论改为“材料未完整读取，暂不能判断是否齐备”，同时显示仍可确定的缺口；不得沿用上面的完整读取文案。

## 6. 原始证据到安全短答

数据顺序统一为：原始证据 → 有完整上下文的语义块 → 安全事实单元 → 本次输出数据 → 渲染。请明确区分保存的数据与展示的数据，完整来源始终保留在既有授权存储，不以摘要覆盖原文。

### 6.1 第一期采用抽取式短答

原台账可能是一段叙述，不能靠任意一句、一个日期或一个 source ID 就证明摘要正确。先建立 SourceBlock：原文文本、来源对象/版本、字段、块内范围、上级标题、项目及规格身份、读取完整性。拆分必须尊重语义和结构，不能把“HD14”标题下的日期移给 HD17，也不能把跨句否定、前提或例外丢掉。

可选取的块应包含一个完整事实及其必要限定。例如“HD17：计划2026-11-06完成测试，仍待油脂到货”应整体保留；不能只显示“HD17 于2026-11-06完成”。一个块依赖前文明确对象或后文例外时，将依赖内容一并纳入；不能安全绑定时不用于确定性结论。

代码根据用户问题选字段，再根据对象、关键词、日期类型及结构选择完整块。优先处理结构化人员/日期字段；叙述性长进展选择最相关的完整块。Qwen 可以帮助提出候选块或排序，但输出只能引用既有 block ID，最终文本由代码从证据取回；未知 ID、跨对象组合、被拆散的条件一律拒绝。

无可靠短块时返回短提示，例如“已找到该项目记录，内容包含多个规格和前提，需要查看原文核对。”并提供查看原文或缩小问题入口。不要自动退回整张台账全文；用户主动展开后才显示完整内容。摘要绝不按字符硬截断，异常回退路径也要遵守这一点。

### 6.2 事实单元与之后的可选增强

FactUnit 至少包含 subject、source_block_ids、claim_kind、status、date_type、date_value、owner、qualifiers、negation、scope、source_revision、read_status。未知字段保持未知，不补一个看似完整的默认值。日期保持来源精度，界面可统一显示 YYYY-MM-DD；计划、实际、预计类型不能混用，也不能凭日期自行推断已完成。

这组字段是内部数据约定，不需要展示给用户。自然语言资料可以先仅生成可核验的抽取式单元。若引入生成式压缩，必须有独立的限定词、对象、数值和状态一致性验证，并证明不会破坏原有 grounding 边界；不能把“evidence ID 存在”当成摘要正确的全部条件。第一批无需为此增加额外模型循环。

### 6.3 统一输出数据

建议使用一个 ResponseEnvelope/ViewModel，名称可随现有工程调整，但至少表达：interaction_id、view_version、subject_refs、task_state、summary、facts、mandatory_qualifiers、primary_action、secondary_actions、detail_ref、source_revision、delivery_state。业务服务不直接组装最终长文；它们返回结构化 data 或 internal event，统一呈现器根据用户、场景与页面状态决定当前内容。

同一数据应支持概览、单字段、详情、来源四种渲染，不让群查询、菜单详情和简报各自维护一套字段语义。所有正常与异常路径都经过契约检查：没有原始 JSON 泄入普通正文，没有非法动作，来源可访问，页面所属对象一致，必要限定完整。

## 7. 节点与状态设计

### 7.1 十个职责明确的节点

| 节点 | 输入与输出 | 运行方式与用户可见性 |
| --- | --- | --- |
| N1 接收绑定 | 事件 → interaction、身份、聊天/话题、原消息、版本 | 确定性；沿用原入站去重，不外发业务正文 |
| N2 任务定位 | 按钮/文本 → intent、请求字段、对象线索 | 按钮/规则优先，必要时 Qwen；不直接回答 |
| N3 对象解析 | 线索 → 唯一对象或有界候选 | 确定性优先；歧义才让用户选择 |
| N4 输入补齐 | 当前任务及已知字段 → 完整输入或最小缺口 | 确定性字段校验；允许批量填槽，不机械一问一字段 |
| N5 读取/业务计算 | 已授权输入 → 资料、业务结果、内部事件 | 复用原服务；只返回 data，不自行 notify |
| N6 事实与约束核对 | 证据/结果 → 安全事实、完整性、冲突 | 确定性主导；少量 Qwen 只提出受限候选 |
| N7 当前内容选择 | 事实及用户任务 → 摘要、详情引用、允许动作 | 确定性；执行预算和优先级，不改业务状态 |
| N8 渲染与预览 | ViewModel → 卡片/完整批准快照 | 确定性模板；有副作用时展示准确对象 |
| N9 执行与回读 | 既有批准 → 业务执行状态/回执 | 复用现有批准、幂等、来源复核与回读；未获准不执行 |
| N10 发布与恢复 | 页面或回执 → 确定发送/更新结果 | 唯一发布口；管理 message_id、版本、重放与 unknown |

只读查询通常走 N1—N8 后由 N10 呈现，不需 N9。创建提醒先完成表单与预览，用户一次批准后 N9 执行；已有明确批准覆盖的恢复或确认继续沿用。后台步骤可以连续完成，用户只面对真正需要输入、选择或批准的节点。

模型调用数量不能由节点数量决定。明确栏目、编号、分页、状态、表单、批准与发送均无需模型；模糊意图、候选排序、资料语义整理才考虑 Qwen。所有模型任务共用现有 ModelCoordinator，不建立各模块自己的并发通道。

### 7.2 交互状态和业务状态分开

交互状态描述用户现在看哪里，例如 selecting、collecting、preview、details、completed_view。业务状态继续使用原事项、计划、发送实例、文稿及挂载状态。打开详情不触发业务重跑，翻页不批准发送，退出页面不撤销已批准计划；确需取消业务时使用明确取消动作。

沿用 am_ux_drafts、am_ux_collection、query_conversations、action_items、reminder_plans、logic_drafts 等既有表。可新增薄的 interaction/view 数据：interaction_id、scope、origin_event_id、current_view、view_version、message_id、subject_refs、pending_task_id、expires。节点只做薄编排，不平行重建事项、审批、调度或挂载的第二套业务状态机。UI 视图可以失效或重新打开，已完成的业务回执不能因此消失。

新问题产生新的 interaction，不能把群+用户的一天上下文当作所有任务的一个页面。旧查询迟到时可以保留为该 interaction 的结果，但不能覆盖用户随后打开的另一项目。每次写视图前比较 interaction、对象与 view_version；失配就记录到对应任务，不抢占当前页。

### 7.3 当前私聊卡和不可变记录

普通私聊浏览、翻页、返回、展开详情，优先更新同一张当前导航卡。维护实际 message_id 与 view_version，按钮绑定卡片版本及授权作用域；更新后旧按钮按现有失效规则处理并提供返回路径。重入首页应恢复或创建一个清楚的当前视图，不把历史几十张卡都当有效入口。

先核验当前应用已有权限下的更新消息卡片路径及实际客户端效果；本轮尚未证明更新接口已在原服务启用。优先复用现有消息能力，不默认申请新的 CardKit 或其他权限。若更新明确不可用，保留一个可控的新结果入口并报告具体限制；结果未知时先核对，不自动新建替代消息。普通旧导航可以恢复最新有效视图，涉及副作用的旧按钮仍严格核对批准版本。

最终业务回执、正式批准快照和必要业务外发保留独立可追溯记录，不为清理 UI 悄悄改写旧的批准内容或“已发送”事实。导航卡可以显示它们的状态与入口。若批准后需要修改正文、对象或规则，必须生成新版本，沿用原有重预览逻辑。

发送/更新的幂等键至少绑定 interaction、view_version、输出类型及对应业务事件。只有明确已拒绝且可安全重试才重试；送达 unknown 不盲目 create 补发。先走核对/恢复流程，报告是否找到原消息。不能用“可能更新失败”作为无限追加新卡的理由。

群卡按共享可见页面设计。JSON 2.0 的共享更新不能被当作个人私有视图；任何展开都只包含原群有权看到的信息。个人事项、私人反馈明细、个人首页放在既有授权私聊路径。不能把群卡点击者的私人数据写回共享卡，也不能借此次改造扩大群或人员范围。一位负责人反馈或翻页，不能因共享卡更新而改变其他负责人的 decision_version、nonce 有效性或原有反馈权；展示版本与业务决定版本分开核对。用双人连续反馈验证，不能只测单人按钮能点击。

## 8. 各业务流具体改法

### 8.1 查询、首页和列表

修复字段枚举后，单字段视图只回答该字段并带必要限定。首页优先显示需要本人处理的事项；台账候选待办和已建 AM 事项各有清楚来源。排序使用已有优先级、明确到期、阻塞、待核验及最近变化，不凭模型猜“最重要”。无可靠排序依据时采用稳定顺序并保留筛选。

列表所有内容随页码切换，不能每页重复全量摘要。项目最多 5 项、每项一个短条目，标题过长可以在详情看完整名称，但不能把编号身份裁没。保留搜索词、筛选、页码和返回位置。多项目查询默认比较本问字段，完整清单可翻页，无须为每个项目生成独立长卡。

### 8.2 提醒、计划和反馈

一次提醒默认只收适用的人、正文和时间；目标群若已由项目入口确定，应显示并允许修改，无须再问。周期选项选择后再出现频率、截止、日历及批准策略。最终预览完整正文只一份，“事项名称”使用真正短标题，不能再复制正文充当标题。

计划首屏显示运行/暂停、下次时间、最近一次结果；完整正文与规则进入详情，发送历史分页。多个 unknown 实例先按具体时间列出，再选择核对。一次计划结束应准确显示无下一次，不能沿用周期文案。

反馈者得到简短“已记录”及必要状态。owner 通知只描述本次谁更新了什么、是否需要处理，完整反馈及来源留在事项详情。先保持现有即时通知时机，解决重复和历史膨胀；批量合并或无变化静默属于后续可选策略，不在本轮擅自改变。用稳定事件键保证持久化、状态投影及通知分别幂等。

通知唯一键采用 business_event/op_id + recipient + notice_kind；从业务服务实际认领或复用的操作身份取得，不只使用平台 event_id 或正文 hash。平台可以为同一操作送来不同回调事件，不同业务时刻也可能合法产生相同正文。分别验证同回调重放、独立重复点击及两位负责人合法同类反馈，不能为了去重吞掉后者。

事项详情默认最新有效反馈与下一步；历史按 5 条分页。迟到、无效、非本人负责等反馈仍可查且标注原因。核验关闭依旧要求证据，工程师“已提交”不能被 UI 简化成“已完成验收”。

### 8.3 进展收集与差异提案

进入收集时清楚显示当前项目/节点/话题及“结束收集”。一条进展从接收、核对到形成提案，更新同一张任务卡，不再额外发送同义状态文本。原话、解析后的事实和精确差异分别可看；解释不确定处集中询问，不能把推断混成已确认事实。

ledger_write=false 时，可做“核对内容”“保存提案”“查看差异”，不展示执行写回按钮，不宣称已经更新台账。已有内部 proposal 状态保留，普通文案明确区分内容已确认与远端未写入。写入开关以后开启不属于此次自动动作。

这里不能仅改按钮文字：新的“确认内容”不得调用 LedgerChanges.approve()，该方法会留下约 600 秒有效的真实写入批准。应使用原有报告人核对能力或独立的 review 状态，不填写 approval，不把 proposal 标为 approved，也不留下开关一开即可执行的旧批准。若未来获准启用写回，应针对当时重新读取的准确 before/after、来源和版本取得新批准，内容核对不能被迁移成执行授权。

结束收集后普通聊天不再自动归入该项目。切换对象时保留旧草稿或明确结束，绑定新版本；引用旧消息仍按原始来源上下文处理，不能随着当前页切换而改归属。

### 8.4 简报与订阅

统一 BriefingData，包含变化事件、待办候选、来源读取时间与完整性、可访问详情。先按项目聚合，首屏最多 3 个当前需要关注的条目；每条说明变化及相关动作，不默认打印 before/after 全文。完整差异按事件分页可达，不用 9500 字符裁剪替代访问入口。

订阅预览承诺哪些内容，实际 payload 就提供同样的类型。主动查询与订阅共享渲染，不共享“已投递即消耗”的状态。旧订阅补入待办前要核对其实际批准快照：原预览已批准包含待办的按批准修复；原来仅批准 changes 或无法还原批准范围的，保持已知范围，不借修复扩大投递内容。新订阅的预览与 payload 从同一模型生成。

首屏只显示前 3 项时，其他变化不能悄悄标为已投递。每次简报应有固定、可访问且符合原权限的完整交付详情，并记录该详情实际覆盖的 event ID 集合；只有随该交付成功提供的事件才能更新投递状态。详情打不开、遗漏某事件或发送结果未知时，不把它算作完成。完整详情绑定本次来源快照，不能把之后才发生的变化一并消耗。无变化是否仍发送、是否只发异常等策略保持原行为，除非用户已有明确决定；不要借简洁改造默认改变投递频率。

### 8.5 预检、文稿和挂载

预检首屏展示检查范围、待补/冲突/专业判断数量及最多 2 个可行动缺口。资料读取不全、合并单元格歧义、要求基线不明确时，主结论必须说明无法完整判断；不能用零缺项或绿色状态暗示通过。完整报告与分析依据仍可打开。补充资料后按版本重检，旧结果标为旧版本，不能继续当当前结论。

文稿整理已存在问题台账及每轮最多两问机制，请复用 question_state.py 与 logic_service.py。已回答的问题不重问，明确无法提供的材料不循环索要；可形成阶段稿时给阶段稿入口与剩余限制。聊天只展示稿件状态、最多两问和下一步，全文放稿件，审阅证据放核对报告。

采用、选择目标、挂载和回读保持独立状态。批准前完整显示准确项目/节点/交付物、当前稿件版本及目标；重复点击复用既有结果。更换资料或目标后按原规则使旧采用/预览失效；结果未知进入核对，不重复上传。此任务可在隔离 port 验证，不为展示界面新挂真实文件。

## 9. 分三批交付，每批都能使用

### 第一批：修确定性错误，立即减少冗余

修统一字段枚举和单栏目视图；一次提醒条件字段与正文去重；暂停/恢复互斥；进展收集只输出一张卡；关闭写回时去掉执行按钮；反馈增量与通知去重；修订阅承诺/payload；删除普通界面的技术 JSON。初步实现完整语义块抽取和有界降级，至少让明确编号和字段查询得到稳定短答。

这一批优先在既有实现内修改，避免为抽象所有模块而拖延修正。保留兼容旧命令的入口，但结果走同一业务数据约定。交付可运行版本、相关检查与少量前后样例。

### 第二批：统一输出与节点

落实 ResponseEnvelope、统一 renderer/publisher、当前私聊视图和版本、interaction 绑定；覆盖查询、列表、简报、事项、进展、预检、文稿的主要路径。将直接 notify 的子节点改为返回 data/internal event，必要的业务外发仍由原执行服务在既有批准下进行。

复用任务池处理群模型任务，验证菜单和无需模型操作在模型忙时仍可推进。完善来源块、事实单元、预算和所有失败/回退路径。不要把旧长文本包装进 JSON 后当作已经结构化，也不要用多 Agent 自由讨论生成界面。

### 第三批：真实体验核验和收尾

在原有已授权范围验证本人私聊导航、真实只读查询及现有卡片操作；手机和桌面分别检查首屏、详情、返回、长预览和可恢复错误。没有真人条件的路径保留隔离证据和准确待验收清单，不制造真实业务动作。

按第 10 节记录少量指标与截图/结构化样例，修复实际阻碍，不扩大成全部历史功能重审。原服务更新按已有有效授权执行，核对唯一消费者、模型 pin、ledger_write=false、相关迁移及可回退状态。报告源码、运行、发布、真实操作和用户验收的各自状态，不用一个“完成”代替全部层次。

下面 16 项是本轮完成标准。数据不足时用合成项目/隔离端口验证，结果标明层次；涉及真实群发、订阅和挂载的部分无已获准对象时不执行。

| 编号 | 操作 | 应观察到的结果 |
| --- | --- | --- |
| U01 | 同项目分别点日期、人员、待办、来源 | 四个视图内容各自正确；不重复整段进展；空信息明确显示未记录 |

| U03 | 长记录含多个规格、预计日期、否定和前提 | 首屏保留完整语义；不能安全压缩时短提示+原文入口；没有裁半句或把计划写成完成 |
| U04 | 连续首页→项目→详情→日期→返回→翻页 | 当前私聊导航卡更新；同一浏览流程不为每步追加新卡；返回位置和筛选保留 |
| U05 | 旧查询运行时打开另一项目，旧结果随后完成 | 新页不被覆盖；旧结果仍归属于原 interaction，可按需查看 |
| U06 | 待办超过一页，翻到第二页 | 正文、按钮、计数都对应本页；不在每页重放全量待办；候选与正式事项可辨 |
| U07 | 创建一次提醒，返回改正文，再确认 | 无周期无关字段；准确正文只一份；旧预览不能执行；仅一个业务计划与一次有效通知 |
| U08 | 选择周期提醒，暂停，再恢复 | 周期字段按需出现；当前状态只出现有效动作；恢复规则预览完整一致 |
| U09 | 同事项两人连续反馈，并重放一次事件/重复点击 | 每人短回执；owner 收增量；完整历史可翻页；重复业务事件不重复通知；不改变既有紧急反馈时机 |
| U10 | 收集一条进展，再结束收集并发普通聊天 | 一条进展只有一张任务卡；原话、解释、差异可查；确认内容不生成写入批准；写回关闭；普通聊天不误入旧收集 |
| U11 | 主动简报后触发隔离订阅投递 | 内容类型与各自批准快照一致；完整详情覆盖的事件才计入投递；主动查看不消耗订阅；同一投递不重复 |
| U12 | 资料有缺项且部分读取失败，随后补资料 | 主结论保留读取不全；不显示全通过；补资料更新当前缺口，完整旧报告可区分版本 |
| U13 | 文稿两问中答一项，另一项明确不能提供 | 已解决/不可提供项不重复问；最多两问；可形成阶段稿时有入口，全文不倾倒进聊天 |
| U14 | 隔离采用、目标确认、挂载及重复点击 | 采用与挂载状态清楚；准确目标和版本完整可查；幂等回执；目标变化使旧预览失效 |
| U15 | 模型忙、卡过期、发送/更新 unknown | 无模型导航可继续；过期可恢复且不丢有效草稿；unknown 先核对，不盲目补发 |
| U16 | 群共享卡操作及手机/桌面查看 | 群卡不出现私人资料且不使其他负责人失去反馈权；两端主操作可见；详情/返回可用；准确长批准内容完整可达 |

记录每个代表场景的：用户动作数、首屏可见字符数、首屏要点数、主/次按钮数、同 interaction 新增消息数、第一次可操作反馈时间、最终结果时间、是否丢草稿。时间从平台收到事件开始记录，区分仅返回 toast 与真正可操作卡片。首个可操作反馈争取 3 秒内；真实模型完成时间按实测如实给出，不提前承诺全流程 3 秒。

普通导航在同一可用会话内目标是只建一张当前导航卡，后续更新；独立新问题、独立批准快照、最终业务回执和必要业务通知可以新增记录。不能为了消息数好看把不同业务事实覆盖成同一条。外发准确预览与必要来源限定的超长不算普通首屏违规，但要说明例外并验证完整性。

测试重点是上述可观察行为和受影响边界。已有对应版本有效检查可复用；增加字段协议、语义块限定、通知幂等、视图版本、unknown 恢复这类有实际风险的检查。不要用大量只断言实现字符串的测试增加计数，不要求重跑所有历史链路或人为凑新的总数。
