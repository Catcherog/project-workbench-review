# 实施与边界

第一批修正统一字段枚举及 None/空字段语义；单字段不再无条件附进展。一次提醒不展示截止和周期批准字段，选择周期后补齐；准确正文只出现一次。进展收集只生成一张任务卡，内容核对与写入批准分离。负责人得到短回执，经理得到新增变化，历史分页；通知与业务记录分别去重。新订阅、计划预览和投递共用内容类型；可还原 UX1 已批准“变化+待办”的按原范围修复，旧 changes-only 或无法还原的保留 changes-only。

第二批新增 source_views、am_views、am_briefing、am_documents、am_presentation 薄层及 ResponseEnvelope。已有服务继续负责业务状态，不另建事项或批准状态机。

| 职责 | 实际落点 |
| --- | --- |
| N1 接收绑定 | am_service.ingest、既有入站表和原消息元数据；scope/原事件固定 |

普通导航记录实际 message_id，后续更新同卡；新问题、准确批准快照、业务最终回执和必要通知保留独立记录。旧查询不能抢占其他 interaction；旧视图写入通过版本比较拒绝。卡过期可重新打开有效草稿，但不会延长资料或批准期限。PATCH unknown 不用 CREATE 补发；CREATE 没有可信 message_id 时保持未知，不把查不到当作未发送。

飞书 raw-card 回读会替换回调值为内部 action ID。本轮使用平台保留的隐藏 element_id 绑定完整发送快照的摘要，同时核对可见文本顺序；不是原始 JSON 字节相等，也不把 update_multi=true 当作更新能力证明。真实更新能力另有成功 PATCH、GET 与桌面显示证据。

群模型步骤提交到原 Gateway 任务池，仍用原 ModelCoordinator 单通道。原业务循环可继续处理菜单和无需模型操作。正常聊天提示采用短答目标；本轮没有以真实 Qwen 通识输出证明所有问题均满足字数/时间目标。

第三批通过真实桌面操作补修来源链接显示、身份未核项目提示及长待办页面；待办最终每页 3 项、项目/历史每页 5 项。人员缺编号按来源保留，不猜 AR 编号。群卡内容、原负责人的 decision_version 和 nonce 继续分开核对。

文稿主要私聊路径返回短结果卡，全文保留在原稿件/附件，报告独立打开；复用已解决、无法提供及阶段稿状态。原群来源文稿继续保留原有私聊附件交付方式，避免将私聊卡错误绑定回群作用域。
