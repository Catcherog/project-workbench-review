## 二、先修投递空等与冷启动

1. 原事件入口已经唤醒循环，但 `am_service.notify()` 写入 outbox 后未通知循环。补齐后台查询完成、outbox 提交、资料读取完成后的唤醒。通知应在事务提交后发生，避免先醒后查不到结果。保留原单消费者，可用事件通知驱动已有 I/O 池；不要靠毫秒轮询或无限线程提速。
2. 回调收到、任务开始、结果入 outbox、投递开始、平台返回分别记录时间，确认约一秒空等被消除。无投递拥塞的热请求以 outbox 就绪至开始投递不超过 50 毫秒为工程目标，实施后实测；不把它描述成现有成绩。处理 event 清除与状态检查的竞态，避免丢失唤醒。重放与并发仍不能重复发卡。
3. 启动或空闲恢复时后台准备固定台账快照；部门树按部门共享，避免每个用户各拉一遍。已有明确本地项目范围不逐次读取远端权限配置。
4. 保留已实现的活跃人员半有效期后台刷新，补启动预热与共享部门树，不重新做另一套身份刷新器；首个未知人员仍需一次可靠核实。源读取与可独立进行的身份读取可并行，结果只能在身份/范围成立后交付。
5. 有符合原快照时效规则的快照时直接给可操作结果及真实读取时间；保留 UX3 的刷新和过期规则，不为提速无限沿用旧资料。无快照时只保留一张加载/结果卡：最终结果若先准备好，应合并尚未发布的加载卡，不再先发布加载卡再排一次结果。已发布或结果未知的加载卡按真实消息绑定继续更新/恢复。缓存未准备好不显示假空目录，也不把加载卡算查询完成。

## 三、按部门内部查询精简检查

### 查询身份与数据

- 继续使用 600 秒身份结论；复用到群只读查询，不为同一人另设一套每次实时核验。
- 身份缓存按可信 app/tenant/open_id 隔离；姓名只展示。当前禁用名单、批准群 ID、项目范围均本地检查。
- 身份后台刷新遇到明确离职、冻结、调岗出范围等否决，立即失效。遇到瞬时网络错误，不提前删除仍在原有效期内的成功结论，也不延长原有效期；到期后核实不成功则停止交付项目内容并给简短恢复提示。
- 部门树与群配置后台维护；多个请求共享一次在途刷新。资料复用 `QuerySnapshots`，目录、详情、字段切换和翻页不重新读台账。
- 根部门用户无需读取部门树。依赖子部门目录的身份结论，其有效截止不能晚于该目录的明确有效期，避免将两层 600 秒缓存叠加成最长 1200 秒；后台预刷新用于减少等待，不延长授权窗口。

### 群查询核验

当前 `GroupLedger.step()` 在处理前后各调用 `guard()`；每次读取群详情、机器人在群、群成员页和联系人，另读整张台账。简单路径按代码推导至少约 11 次飞书请求，尚无本轮群实测数据。

改为：已批准群 ID/该群项目集合本地查表＋600 秒人员结论。来自原可信飞书入口的当前群消息事件可证明这次发言的操作者与群关系，不再逐问扫描全群成员。卡片第一次绑定、旧卡来源异常、平台明确报成员/群失效等情况再做必要补查；群信息变更后台维护，管理和真实发送仍执行其必要业务校验。

私聊允许 TH2 全固定台账，不自动变成所有群可见全部台账。复用原 `group_ledger.disclosure`，不扩大已批准群及项目范围；群目录、搜索、计数、来源链接、字段详情统一按这个集合过滤。

### 保留的轻量边界

保留 app/tenant/user/chat/thread、role、nonce、消息绑定、视图版本、事件去重、当前本地范围。这些是便宜的本地比较，用于防止串人、串项目、乱序和重复操作。查询能力不能变成 owner 管理权；`unknown` 不当作未发送。

完整回读已经在独立 `verification_pool`，不再安排一次“移到后台”的重复改造。普通只读发布有可靠成功回执后，不再逐张完整 GET 核验。改为发布验收样本、抽样、异常/未知恢复时回读，减少后台请求；明确区分“发布成功”和“独立核验成功”。这项改动主要减少总请求与资源竞争，不能把后台 GET 耗时再从目前首次发布耗时中扣掉。批准、反馈记录、真实外发等业务流程保留与其结果有关的核验，不把只读抽样策略套用到业务动作。

### 热路径调用预算

下表是实施目标，不是本轮已测结果。后台共享刷新与具体用户请求分别计数。

| 场景 | 人员/群远查 | 读台账 | 模型 | 显示结果 | 正常完整回读 |
| --- | ---: | ---: | ---: | --- | ---: |
| 私聊热浏览 | 0 | 0 | 0 | 一次更新；直接回卡后额外 PATCH 为 0 | 0，抽样除外 |
| 已批准群的明确项目热查询 | 0 | 0 | 0 | 一次公开回复 | 0，抽样除外 |

直接回卡仍需要处理飞书回调，不称为“完全无网络”。新用户身份、真正失效的源快照等冷路径单列，不能混入热缓存预算。

## 四、群查询接入同一套快服务

当前 `am_query.query_request/query_grant` 限制 p2p，群回复仍是纯文本；不能把私聊卡片原封不动发群。增加明确群入口与展示适配，复用目录、快照、字段提取、版本和有界投递能力。

- `@AM 项目`、`项目列表`、准确编号/名称/已登记别名、四栏目、明确引用追问，先走确定性代码；这些操作零新增模型调用。
- 名称唯一匹配时直接回答；歧义显示可点候选。只有真正需要语言理解的输入才使用原 Qwen，不为首次明确名称先调 intent 模型。
- 群只读 I/O 使用已有有界查询任务池，不在主循环同步等待群 HTTP，也不把整段鉴权/拉表占在 model pool。确需模型的部分才进入唯一模型通道。
- 保留当前主动 @ 才处理的边界；不监听普通群消息自动插话。
- 回答数据标真实 `observed_at`，保留来源必要条件、未验收状态和适用范围，不在快照展示时重写成当前读取时间。

## 五、群里怎样使用

### 公开问答保持短而明确

`@AM 某项目谁负责/进展怎样/什么时候/下一步`：在原消息或话题回复一张公开短答。问谁就答人员，问进展就答少量要点，附资料时间与必要条件；不附无关整段台账。公开答案作为讨论依据保留，其他人浏览目录不能覆盖它。

### 目录和连续浏览只给操作者

`@AM 项目`：打开该群范围内、仅提问者可见的目录，默认 5 项，名称＋可证实的负责人/状态；搜索辅助，空搜索仍显示列表。项目详情沿用 UX3 四个直接栏目及实际文案，返回保留页码。另一人点入口得到自己的视图；分页和切栏目不向全群广播。

公开答案上的浏览按钮应创建该操作者的个人视图，不能通过 callback 直接替换原公开消息。直接回卡只适用于已经绑定当前 actor 的个人卡。普通公共卡不显示 owner 管理按钮；项目负责人自己的个人视图才提供跟进入口。

优先验证飞书 ephemeral 指定人可见群卡，再验证其 schema、更新方式、话题群及有效期。官方存在该能力，不等于当前 schema 2.0、独享更新和话题投递组合已验证。不要直接认定 `update_multi=false` 能用于当前 2.0 卡。只做最小兼容验证，记录真实限制。

官方依据：[消息 API 概述](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1)列有 `ephemeral/v1/send`，用于向群中指定用户发送仅其可见的卡片。当前 2.0 卡片与该接口、回调更新、话题群的组合仍以最小实测为准。

若当前组合不支持可靠的个人群内浏览，按钮清楚标为“私聊继续”，携带稳定项目/来源群上下文进入现有私聊卡；从群目录承接的私聊视图仍保持原群项目范围，想看全台账须用户另开正常私聊查询入口。公开问答仍在群内。不要为了适配重建网站、整体降级或强制所有问题转私聊。

### 引用和多人追问

明确引用 AM 的公开项目答案再 @追问，按 bot 消息绑定找稳定项目 ID；允许同群其他已授权同事引用，使用当前人的资格与当前群范围重新过滤。不能借用原提问者的私聊权限。没有明确引用时，只承接同 actor/chat/thread 的上下文；不猜整个群最近讨论的项目。多项目答案无法唯一确定时给可点选择。

### 项目负责人群内发起跟进

从个人项目视图进入现有预填表单和准确预览，目标项目、群、事项只带入已核实信息；草稿不铺进公共群。实际发送继续原准确确认及幂等规则。工程师反馈、私聊补填和个人回执复用原实现；查询点击不新增提醒、订阅或真实业务发送。

## 六、直接回卡的采用条件

UX3 已有无业务内容卡的协议实验，但生产项目浏览仍为异步 PATCH。先完成唤醒修复再比较收益；有本地快照、有效身份和可验证绑定的导航可直接返回卡片，避免额外 PATCH。慢源、身份过期、模型任务继续异步，不在回调线程等待慢网络。

同步响应返回不自动等于平台已应用；同一版本不得又回卡又排队 PATCH。保留版本有序与未知结果处理。平台 3 秒回调期限不等于用户 3 秒内见到有效结果；toast 或加载卡不算完成。

## 七、定向验证与回传

沿用原环境与脱敏副本同组验证，不追求增加测试数量。重点覆盖：

1. 热缓存连续查询不查通讯录、不拉表、不调用模型；投递等待不再固定约一秒。
2. 冷请求、资料慢、身份瞬时刷新失败与明确否决分别正确；原有效期不延长。
3. 两名合成用户在同群各翻不同页、切不同栏目，公共答案不变，私有视图不串人；群/范围本地变更及时生效。
4. 原提问者和另一同事引用 AM 答案追问，项目正确；无引用不借用他人上下文。
5. 模型忙、慢群请求、慢发布时，其他热查询仍可处理；乱序与重放不覆盖新页或重复发送。
6. 桌面及可用手机条件下检查公开/个人可见性、正确话题位置、长名称、返回与过期恢复；不可实测的明确待验收。

在同一最终源码版本做一组代表性真实只读操作，覆盖目录、翻页、栏目、明确名称查询、引用追问及冷请求；真实测试仅在既有授权范围内进行。按版本和冷热分别记录全部成功与失败样本，列入站、初次任务开始、资料等待/恢复、outbox ready、投递开始、平台回执、客户端可见及必要核验时间。计算/网络累计值和墙钟值分开；冷请求恢复不是初次排队，客户端时间未测就标未测。

原 3 秒体验目标继续保留：先把常用热浏览稳定做到 3 秒以内，同时单列首次读取/身份到期等冷路径；冷结果仍超过 3 秒或客户端可见时间缺证时，整体目标仍为未验收。报告实际范围、成功率和超时原因，不能只统计回调 toast、拼接不同代码版本或凭少量成功样本宣布长期 P95 达标。
