# 隔离工作台：实际操作体验记录

日期：2026-10-14。操作者：执行端助手。产品实现：`caea175db812540537d631aa17800c5b1b19df66`，本轮没有修改产品代码。

**总体判断：主要流程能完成，简单记录的返回与撤销反馈较清楚；集中协作目前偏费阅读、费滚动，尚不能评价为轻松上手。另发现一处需要优先修复的跨工作区回执显示问题。**

这是我实际操控后的界面观察与判断，不是用户本人验收，也不是新用户研究。我已参与实现、熟悉步骤，因此这轮不能给出真实新手完成率、学习时间或人类操作耗时。以下把实际现象、使用影响及建议分开记录。

## 四个维度的结论

| 维度 | 本轮判断 | 依据 |
|---|---|---|
| 是否便捷 | 简单记录基本顺畅；协作和恢复偏绕 | 记录保存后回到原清单，可直接查看/修改/撤销；两条短消息的保存动作却位于长页下方，状态反馈又在页头。 |
| 是否符合常见办公习惯 | 部分符合，动作含义仍有歧义 | Esc 返回并保留草稿、Tab 焦点、明确撤销符合预期；本地记录按钮叫“发送”，同页又有真正的消息执行，容易需要额外辨别。 |
| 理解难度 | 偏高，熟悉业务也要理解一套界面术语 | “候选纳入、批准、整批执行”需要分清，但主层又加入指纹、批次身份、回读、执行接口等词；变更或阻塞提示不总能指向具体对象。 |
| 信息密度 | 分配不均，重点与次要内容的权重不合适 | 本次样件事项在清单页距顶约 698px；两条短消息展开后页面高约 2464px。技术标识和重复说明占空间，下一步动作反而远离当前阅读位置。 |

白色正文底、文字对比度和分区边线总体可读，当前最需要改善的是层级、反馈位置和动作距离。建议通过收纳次要信息、突出当前动作改善，不靠继续缩小字体。

## 我实际操作了什么

使用本机当前已打开的隔离版，经浏览器实际点击、输入、文件选择、键盘返回、滚动、窗口尺寸变化与刷新操作；没有用接口直接代替页面保存/批准/执行。辅助卡按钮仅用于制造另一入口的合成版本变化或取消。后台只读快照用于核对显示事实。

| 场景 | 实际操作和结果 |
|---|---|
| 原事项与文本输入 | 从清单打开“验收样件跟进”，进入“记录进展 / 讨论”；输入草稿后按 Esc，回清单且焦点回到原事项；重新进入仍有草稿。再保存“已收到第二批验收样件（本轮操作体验）”，收到本地回执并返回清单。 |
| 图片、空日期校验、撤销 | 通过原文件选择器添加合成图片，看到上传中状态及文件名；尝试填写日期时操控工具未写入原生日期控件，实际日期仍为空，触发校验。退回“未提供”后保存图片，再明确撤销这次自己的图像操作；回执显示已撤销。 |
| Q01 独立决定与执行 | 只纳入候选，没有发送；再分别勾选两条消息并保存批准，仍未发送；展开本批范围后明确执行，得到两条模拟发送回读结果。刷新并进入“历史与结果”，两条记录仍在。 |
| 版本变化后的恢复 | 先勾选两条消息，再由辅助卡模拟外部修改第一条；重新读取后第一条退出选择，未变的第二条保留；明确重选可继续保存。候选事项版本变化后也需重新勾选，随后可单独纳入。 |
| 只读草稿恢复 | 留下未保存草稿，由另一入口取消消息，重新读取后仍可展开草稿并明确放弃；另一条已批准消息恢复可执行。放弃后刷新，草稿没有复活。完整服务器状态及模拟发送数均未变化。 |
| 键盘与窗口 | 实际使用 Esc、Tab、⌘Enter；Esc 与 Tab 有效，Tab 可见焦点；这次 ⌘Enter 没有提交，页面也未显示此快捷键说明。比较本机默认视口 1299×1344、1024×768 与 1440×900，结束后恢复默认尺寸。 |

这轮**没有评价真实模型的理解质量**，也没有验证真实消息送达；模型和收发仍是合成适配器。原生日历选择受到本轮操控工具限制，不能将首次填值未生效直接认定为产品日期功能缺陷。

## 优先发现

### U-01：切换工作区后，旧回执串到新工作区，而且撤销状态变回“已保存”

**优先级：高，需要先修复。此项是确认的显示错误。**

实际路径：在 01 号保存本轮图像记录 → 明确撤销 → 回执显示“本次操作已撤销” → 切换 02 号工作区并进入助手。页面仍保留 01 号的旧回执，标题却变为“本地记录已保存”，且仍显示查看、修改、撤销等按钮。重新读取页面状态后仍如此，整页刷新才消失。

独立后台读回：01 号该操作存在 `undoneAt`；02 号没有这条进展，也没有对应保存回执，revision 仍为 1。**当前确认的是跨区显示残留，未发现跨区业务写入。**本次合成工作区存在相同事项 ID；不据此声称已经覆盖所有工作区组合。没有尝试点击错区回执中的修改/撤销按钮，相关按钮的后续影响还需定向验证。

这会破坏最基本的使用预期：切换工作空间后，用户应能相信当前页面只在陈述当前空间的结果。建议回执同时绑定工作区与操作身份；切区后清理旧展示，缺少对应持久回执时不以缓存显示“已保存”。

证据：[错误显示截图](screenshots/11-cross-workspace-stale-receipt.png) · [两工作区读回](evidence/cross-workspace-receipt.json)。

### U-02：关键成功/失败提示留在视口外，点击后容易感觉没有反馈

**优先级：高，影响错误恢复和操作信心。**

两个实际例子：

- 在 1024×768 窗口，空日期校验错误的顶部约为 `-385px`、底部约为 `-295px`，整个提示都在当前视口上方。当前可见的是日期字段和发送按钮，字段旁没有直接指出错误；上方还保留着上一条绿色保存回执。
- 在 1440×900 的协作长页，点击底部保存决定后，“所选决定已保存；本次没有发送消息”位于约 `-1251px`，不在点击处可见范围内。

提示文字本身多数准确，但位置让用户需要主动寻找，重复点击或误判结果的可能性会上升。建议字段错误就近显示并把焦点带到问题处；保存成功与当前已选/已批准数量放在操作区域附近，必要时使用持续可见的轻量状态区。

证据：[空日期时的当前视口](screenshots/08-date-validation.png) · [成功反馈不在当前视口](screenshots/15-success-feedback-out-of-view.png)。

### U-03：输入与协作主动作离当前内容太远

**优先级：中高，属于高频操作负担。**

在已有一条历史记录的输入页，1024×768 下新输入框从约 `y=726px` 才开始，提交按钮约在 `y=1176px`。历史回答与上一条回执先占据大部分空间，用户本次要写的内容和主动作落到下方。

两条短协作消息在 1440×900 下，页面高度约 `2464px`，保存决定按钮初始位置约 `y=1979px`。消息完整展示有价值，但重复的收件信息、技术身份、边界说明和编辑区域，把“阅读—选择—保存”拉得很开。仅纳入一个候选也要经过整批正文才能到保存区。

建议优先做：输入区与主提交动作保持容易到达；消息默认提供紧凑、完整可读的正文，编辑时再展开编辑器；在同一可见操作区显示所选范围、保存决定、核对执行范围及即时结果。Q01 两步分离继续保留，不将批准和发送合并。

本轮有滚动操作，但工具定位点击会自动滚到目标，平滑滚动也存在观测时差。因此不把工具滚动次数当成人类操作成本；这里采用的是实际布局高度与按钮位置证据。

证据：[小窗口输入位置](screenshots/04-compose-1024.png) · [两条消息预览首屏](screenshots/13-two-message-preview-top.png)。

### U-04：技术词语与常显标识增加理解成本，业务结果信息不够突出

**优先级：中。**

实际常见文字包括“保存修改并回读预览”“依据与当前预览指纹”“执行接口按整批处理”，以及长批次 ID、事项 ID、消息 ID。两个尚未处理的消息也被顶部称为“历史与结果 2 条”，容易把总记录数与已处理结果混在一起理解。

结果卡直接显示长消息 ID，但本轮没有在常显结果中看到直接的发送时间；批准历史里另有时间，不能替代发送时间。另一方面，本地输入用“发送”作为提交按钮，会与真正对外执行消息混淆。

建议让主层先说明“对谁、什么内容、现在是什么状态、接下来做什么”；保留全部审计字段，但把 ID、指纹和接口细节放进可展开的技术详情。用业务结果解释按钮作用，保留纳入、批准、执行三者的区别。既有五入口不重新设计，可在风险页更清楚地区分普通待办与风险事项，降低“普通工作为什么在风险里”的理解负担。

### U-05：恢复入口已具备，但定位与变更解释还不够直接

**优先级：中。DEV1-B01/B02 的技术关闭结论不因此重开。**

本轮已确认：旧选择退出、有效选择保留、新版明确重选，均能继续；只读草稿的“不是发送记录”和“不改变消息”说明清楚，放弃后也没有写入或发送。

体验上的欠缺是：

- 外部只修改正文后，“本次业务前提变化”可以展开，但里面只有标题，没有显示变化内容。用户仍需重新阅读正文来寻找修改点。
- 候选版本变化时显示“版本 2”，但没有在候选框说明具体改变了什么。
- 整批被草稿阻塞时，只说存在未保存/过期草稿，没有直接指出哪一条或提供“去处理该草稿”的入口。使用卡已经告诉我在哪条消息里，所以本轮比没有指引的新用户更容易找到。

建议就近标出“哪条已更新”及必要变更内容；阻塞提示直接关联到对应草稿。缺少可显示差异时，不显示可展开却为空的变化栏。

证据：[展开后为空的变化说明](screenshots/18-version-change-explanation.png) · [只读草稿恢复入口](screenshots/20-readonly-draft-recovery.png) · [放弃前后后台不变](evidence/discard-readback.json)。

### U-06：几个较小但会累积的摩擦点

- 同一事项中同时存在“设置时间 / 记录进展”和“记录进展 / 讨论”，初次选择需要辨别；统一主入口、让时间安排作为明确的次级动作会更直观。
- 进入新的输入过程时仍展示旧的“本次保存回执”；有时间戳，但建议更明确标为“上次已保存”，避免和当前未提交输入混淆。
- 图片上传有上传中状态、文件名与移除入口，这是有效反馈；但没有缩略图，而且原生文件控件随后显示“未选择任何文件”，确认选图主要靠文件名。
- 本次只有少量事项，清单前仍展示多项为 0 的分类，控件占比高。大量真实数据下筛选的价值尚未评估，不建议简单删功能；可收纳次要/空分类而保留可达入口。
- 验收工作区下拉顺序为 1、2、4、3。这是本次合成场景命名/ID 排序造成的辅助材料问题，单独登记，不归为已审核心功能缺陷。

## 哪些地方值得保留

原事项标题和归属始终可查；Esc 返回能保留草稿且回到原事项，Tab 有可见焦点。单条保存后回执有内容、时间、查看/修改/撤销入口，能返回原清单，减少来回导航。撤销后标题明确变为“本次操作已撤销”。

完整正文、收件人和渠道能够在执行前核对；Q01 保存决定与执行保持分开，结果刷新后可重入。FIX1 两种恢复都可继续，且明确放弃草稿只影响本地缓存。这些行为有实际可用价值，优化应保留这些边界。

## 本轮留下的状态与建议顺序

用户先前的“已收到验收样机”进展逐字段保留。本轮另留一条明确标注“本轮操作体验”的文本进展；本轮图像操作已经撤销，历史原件按原产品规则留存。02 号完成 **2 条模拟发送**；03 号完成纳入与批准但未发送；04 号消息一取消、消息二仍已批准未发送，本地体验草稿已放弃。没有真实业务外发，没有启用调度。

建议先处理 **U-01 回执作用域**与 **U-02 提示可见性**，再改善主动作距离、技术信息分层和恢复定位。无需为已经关闭的 DEV1-B01/B02 追加 FIX2；这些新体验发现单列。本轮仅评估并记录，没有修改已审代码，没有自动进入新一轮开发。

用户本人验收继续待反馈；复杂真实模型后段、同事链、持续接收分别保留原待办。本轮不以技术流程完成代替“使用体验已通过”。
