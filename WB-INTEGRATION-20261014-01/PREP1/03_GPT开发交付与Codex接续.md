# GPT 开发交付与 Codex 接续

## 本轮分工

用户已明确扩展三方协作：GPT 在规划和必要对齐后，直接完成当前环境可开发的代码与文件；Codex 负责需要本机、工程仓库、外部系统权限的实际接入和验证。用户负责影响工作方式、业务含义、重要交互或新增真实写入的决定。

不因缺少原仓库写权限而停在“建议让 Codex 开发”；也不把聊天产物写成已落入产品。现有工程使用 React/TypeScript 和本地服务，沿用依赖和架构，不另起一套应用或更换框架。

## GPT 下一轮先交什么

阅读本轮材料后，先给出按页面/组件/接口分解的合并方案和文件改动表，明确每一项的输入、用户动作、保存结果、去向、失败恢复、验证场景及依赖。

每轮只问一类真正影响使用的问题，最多 3 个。能由基线或源码确定的技术问题自行判断；回答未到时继续不依赖它的工作。已确认的五入口、信息分层、原事项复用、完整预览、分别批准、未知先查、整次冲突撤销、Astra/max、允许使用测试项目等不重问。

候选待决项仅在具体方案确有选择时提出，例如“若分批验收，首批覆盖到哪个完整使用链”和“最终使用验收希望先看哪些高频场景”。不要把所有可能的选项都变成前置问卷；外部真实对象的选择只阻塞对应外部测试。

## 可直接开发的部分

- Apple 风格设计变量、导航与布局、稳定阅读层，及必要的局部样式。
- 共享回执、处理状态、完整消息预览、批准记录、待决定和异常结果的组件。
- 依据现有服务返回数据的显示适配、页面上下文与返回行为、纯函数和合成场景测试。
- 已取得完整上下文的组件修改和精确补丁；接口与关键业务状态以当前源码为准。

最小完整交付以一个能核验的使用链为单位，不只给效果图、伪代码或空壳。若缺某个必要依赖，只列那个文件/导出符号及其用途，同时继续独立部分。

## 每批文件的交付格式

1. 明确任务/轮次，例如本任务 `PLAN1` 与 `DEV1`，采用本轮固定审核 SHA 和产品基线 `319869a4…`；不要另起互相冲突的基线。
2. 文件清单：仓库相对路径、add/modify/delete、输入文件 SHA-256、职责及依赖。修改尽量提供完整最终文件或可精确应用的补丁，不用省略号替代必要代码。
3. 保留原业务函数/接口/请求与审计参数的说明；新增状态只在 UI 展示层使用，未经依据不另建业务状态机。
4. 验证记录：实际做过的静态/组件/合成测试及结果；未运行的完整构建、产品浏览器或真实接口另列。模拟发送、手工函数转录实验不可写成真实产品结果。
5. 可以直接在对话提供完整核心文件，文件多时附最小 ZIP、目录说明与校验清单。附件只是交付载体，不需用户手工重打包；正文必须保留来源、关键决定和接续定位。
6. 将需要 Codex 写入的工作单独写为“本轮执行交接”，列实际文件、精确接线点、适用的用户决定、验收结果与停止点。接收方实际读取聊天和必要附件后再落地。

## Codex 后续接续模板

执行本任务经用户实际启动的 DEV/INTEGRATE 轮次。读取规划对话中明确标出的“本轮执行交接”及指定核心文件，记录实际采用要求、消息截止、附件版本与指纹。

从产品 `319869a4ae35be801ec3120884cefa2951d8ce19` 核查当前真实状态后建立或复用独占隔离工作树；若有更新先核对相关差异，不能重置共享主目录或覆盖较新工作。将 GPT 文件按精确路径接入，保留来源与必要修改说明。缺少写权限只暂停相关动作，不停掉已有授权的实现与模拟验证。

使用独立数据和端口，明确测试模式，保留原验收副本。完成相关构建/类型检查及真实浏览器操作；核对页面→接口→持久记录→刷新回读，覆盖成功、失败、未知、冲突、部分保存与返回。真实通道仅按具体对象和本轮授权执行；既有一次性 A1 授权不扩为自动发同事消息。

回传到现有审核仓库本任务下的新轮次，保存实际差异、最终核心文件、验证与限制；远端固定提交读回后给 GPT 审核入口。不会因为审核通过自动安装、生产迁移、启用持续调度或 push/merge 产品源码。
