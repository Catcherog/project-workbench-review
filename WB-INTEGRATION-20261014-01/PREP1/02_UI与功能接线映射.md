# UI 与现有功能的接线映射

本表基于本包固定源码的静态核对，用于合并设计，不是已完成接线的报告。优先复用现有行为，将 UI R2 的视觉、信息分层和操作恢复方式接到现有状态。

## 页面与组件

| UI R2 入口/能力 | 当前产品落点 | 合并约束 |
|---|---|---|
| 项目、风险、数据、周例会、助手 | `app/workbench-v2.tsx` 的 `mainNav`；内部 view 为 overview/attention/inbox/weekly/assistant | 五入口和现有 URL/返回上下文保留；原型 projects/risks/data 等名称需做映射，不能新开另一套业务状态 |
| 同事项侧层，现状→操作→依据/历史 | `item-workspace.tsx`、`work-item-panel.tsx`、`work-item-entry.tsx` | 保留原事项稳定身份、上下文导航、输入草稿、焦点与列表位置；避免复制事项 |
| 统一图文输入、手动时间 | `WorkItemEntry`、`InputImages`；`/api/v2/attachments`、`/api/v2/codex/jobs` | 原图身份与顺序、发生时点、请求身份、版本及依据参数沿用；移除原型日期正则和假保存逻辑 |
| 保存回执和历史显示 | `P1Receipt`、`workItemInputLabel`、`CorePreparationResult` | 从持久回执读保存结果；纯图标签不再落成“手动时间安排”；后段未完成单列 |
| 暂停/恢复/优先级/候选纳入 | `WorkItemCoreControls`、`/api/v2/work-items` | 原型按钮只是展示参考；沿用实际日历、权限、有效等级与版本冲突检查 |
| 依赖和资料准备 | `CorePreparationResult`、`lib/work-item-dependencies.ts`、`scripts/core-work-agent.mjs` | 展示依据、最低时长/窗口/缺口和候选方案；准备结果不改成已执行协调或已交付 |
| 集中完整消息预览与结果 | 全局 `CoreCollaborationPanel` 与原事项面板；`GET /api/v2/core` | 使用同一批次/消息身份；待审、已处理和待决定都有可重入入口，不随 pending 数归零而消失 |
| 批准、取消、部分接续 | `scripts/core-collaboration.mjs` 的 decide/execute；原型 B01 动线 | 编辑先保存并取得新指纹，再批准实际正文；候选纳入 admissions 与消息 decisions 分开，已有批准不重放 |
| 未知结果、明确失败、人工接手/交回 | reconcile/authority/execute 原接口 | 消息状态 stage 与执行权 executionOwner 分开，接手不等于发送成功或事项关闭 |
| 整次撤销 | `P1Receipt`→`p1-undo`；原 operationId | 跨相关对象先完整冲突检查；有后续修改时整次不撤销，保留较新人工决定和已发事实 |
| 样式和导航外壳 | 本地入口可达的 `workbench-v2.css` 等 36 份 CSS；另附 Next 入口的 `globals.css` 对照 | 玻璃用于导航/工具栏/浮层，正文用稳定底色。本地构建入口是 local-entry.tsx；globals.css 由 layout.tsx 引入，不在该 36 份中。逐处处理层叠，不全局覆盖全部 button/input，也不删除业务面板 |

## 不能一对一替换的状态

| 原型状态 | 正式整合必须保持的语义 |
|---|---|
| `state.receipt` 或原型 saved | 输入理解、业务保存、后段准备、页面刷新分别表达。`job.status=completed` 不自动等于业务已保存 |
| 原型 failed | 区分提交前失败、业务已保存但刷新失败、后段准备失败，不能都引导重新提交 |
| 原型 pending/sent/unknown/manual | 对接 pending_review/approved/sending/sent/readback_verified/failed_not_sent/unknown/needs_preview/blocked/stopped/cancelled；`executionOwner=human` 为另一维度，不能覆盖真实发送状态 |
| “已发送” | `sent` 与 `readback_verified` 保留差异；发送不等于已读、知晓、认可或业务完成 |
| 原型 `decisionApproved` | 读取实际 approvalHistory、消息指纹、纳入结果；缺失历史正文如实标缺，不补造记录、不重新发送 |
| 原型 `lastOperation`/数组快照 | 不作为撤销依据；复用后端 operationId、相关对象冲突检查和既有 p1-undo |
| 原型 `window.openai.widgetState` | 仅为原型持久演示；产品数据仍走原 HTTP/SQLite/审计，草稿缓存不成为业务真相 |

## 字段级接线要点

- 统一输入：`workspaceId/requestId/sessionId/contextRef/text/sourceIds/attachmentIds/p1Input`；原 `occurredAt`、`expectedVersion/expectedBasis/expectedEvidenceBasis`、手选检查/完成时间不得丢弃。响应未明时用同一 requestId 查询原任务，不换新 ID 盲目重发。
- `POST /api/v2/core`：准备用 `prepare-messages`；编辑/取消/批准用 `decide-messages`，参数为批次 `sourceId`、`requestId`、`decisions[{id,fingerprint,action,...}]`，可独立附 `admissions[{id,expectedVersion}]`。联合确认沿用服务的事务和前置条件，不能一勾全批准。
- 执行用 `execute-messages`，查询用 `reconcile-messages`。执行前重新核对来源、对象、收件人、正文、批准范围和执行权；变化需重预览，明确失败才能按条件重试。
- 接手/交回请求为 `action:message-authority`，另传 `authorityAction:takeover|release`，附 `sourceId/messageId/expectedFingerprint`；不能把外层 action 直接改成 takeover。
- 本人/同事输入回执分支不同。R2 对同事新增 `save.status/save.receipt/preparation/failureCode` 等独立信息，沿用实际返回值，不能把消息已接收显示成业务已保存。
- 附件预览应显示现有实际原件身份/权限/读取结果。原型批准消息中的空附件列表不能证明真实原生附件发送已实现；需要能力扩展时单列，勿为了 UI 对齐创造后台支持。

## 给 GPT 的实现次序建议

1. 先锁定视图与状态映射，复用全部已确认业务规则；列出真正未定的交互取舍。
2. 做外壳、阅读层、共享状态/回执展示及消息卡组件，保留旧行为回调和属性契约；从用户最常用的原事项输入→回执→返回链验证。
3. 接入集中预览/待决定/结果重入，覆盖部分批准、变更后重预览、失败与未知、接手/交回、整次撤销。
4. 扩展到其他四入口并做样式冲突、长内容、批量、键盘与窗口检查；再分开安排真实模型后段、同事链、持续接收和用户业务验收。

顺序是本轮供规划的技术建议，不新增用户业务批准，也不要求先等所有真实通道开放才能完成前端与合成验证。
